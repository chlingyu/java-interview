# 10-Redis

---

## 一、基础
### 1. Redis 的数据类型有哪些？各有什么应用场景？

**Redis 有 5 种基础数据类型 + 3 种特殊类型。**

| 类型 | 底层实现 | 应用场景 |
|------|---------|---------|
| **String** | SDS（简单动态字符串） | 缓存、计数器（`INCR`）、分布式锁（`SETNX`）、Session |
| **Hash** | ziplist / hashtable | 存对象（如用户信息），字段级别增删改 |
| **List** | ziplist / quicklist（双向链表） | 消息队列、最新消息列表、关注列表 |
| **Set** | intset / hashtable | 去重、共同关注（交集）、抽奖（`SRANDMEMBER`） |
| **Sorted Set（ZSet）** | ziplist / **跳表 + hashtable** | 排行榜、延迟队列、带权重的排序 |

**三种特殊类型（Redis 2.8.9+）：**

| 类型 | 用途 |
|------|------|
| **HyperLogLog** | 基数统计（如 UV 统计），内存固定 12KB，误差约 0.81% |
| **Bitmap** | 位操作，适合签到、在线状态等二值场景 |
| **GeoSpatial** | 地理位置，附近的人、距离计算 |

**这题面试经常挖坑：ZSet 的底层为什么用跳表不用红黑树？**

跳表实现更简单，范围查询（`ZRANGEBYSCORE`）更高效（链表顺序遍历即可），且可以通过调整层数在时间和空间之间灵活权衡。Redis 作者 antirez 说过「跳表更好实现和调试」。

**背诵口诀：** 五大类型：String 缓存计数、Hash 存对象、List 队列、Set 去重交集、ZSet 排行榜。

> 面试话术：「Redis 有 5 种基础类型：String、Hash、List、Set、ZSet。String 用于缓存和计数器，Hash 存对象字段，List 做消息队列，Set 去重和集合运算，ZSet 做排行榜。特殊类型有 HyperLogLog（基数统计）、Bitmap（位操作）、GeoSpatial（地理位置）。」

### 2. Redis 为什么这么快？

**Redis 单线程（指命令处理是单线程）每秒能处理 10 万+ 请求，原因有五个：**

| 原因 | 说明 |
|------|------|
| **纯内存操作** | 数据存在内存中，读写速度是磁盘的 10 万倍 |
| **单线程无锁竞争** | 避免了线程切换和加锁开销，不存在死锁 |
| **IO 多路复用** | 用 `epoll`（Linux）一个线程监听多个 socket，高效处理网络 IO |
| **高效的数据结构** | SDS、跳表、ziplist、intset 等都针对性能做了优化 |
| **单线程执行命令** | 命令顺序执行，避免了并发问题 |

**这题面试经常挖坑：Redis 是完全单线程吗？**

**不是。** Redis 6.0 引入了**多线程 IO**：网络读写（收发数据）用多线程，但**命令执行仍然是单线程**。这样既利用了多核做 IO 又保证了线程安全。

此外，Redis 的**后台任务**一直是多线程的：持久化（RDB fork 子进程、AOF rewrite）、惰性删除（`lazyfree`）都在后台线程中执行。

**背诵口诀：** 内存快、单线程无锁、epoll 多路复用、数据结构高效。6.0 后 IO 多线程，命令仍单线程。

> 面试话术：「Redis 快的核心原因是纯内存操作、单线程避免锁竞争、IO 多路复用高效处理网络连接、高效的底层数据结构。Redis 6.0 引入了多线程 IO 处理网络读写，但命令执行仍然是单线程的。」

## 二、持久化
### 3. Redis 的持久化方式？RDB 和 AOF 的区别？

**Redis 支持两种持久化方式：RDB（快照）和 AOF（追加日志），可以同时开启。**

| 对比项 | RDB | AOF |
|--------|-----|-----|
| 原理 | **定期生成**内存数据的二进制快照 | **每条写命令**追加到日志文件 |
| 触发方式 | `save`（阻塞主线程）/ `bgsave`（fork 子进程） | 每次写命令后追加 |
| 文件 | `dump.rdb`（二进制，体积小） | `appendonly.aof`（文本，体积大） |
| 恢复速度 | **快**（直接加载二进制数据） | 慢（需要逐条重放命令） |
| 数据安全 | ⚠️ 可能丢失两次快照之间的数据 | ✅ 最多丢 1 秒数据（`everysec` 策略） |
| 文件大小 | 小 | 大（需要定期 rewrite 压缩） |

**AOF 的三种刷盘策略：**

| 策略 | 说明 | 安全性 | 性能 |
|------|------|--------|------|
| `always` | 每条命令都**同步刷盘** | ✅ 最安全，不丢数据 | 最慢 |
| `everysec`（**默认推荐**） | 每秒刷一次盘 | 最多丢 **1 秒**数据 | 折中 |
| `no` | 由操作系统决定何时刷盘 | 可能丢较多数据 | 最快 |

**AOF 重写（rewrite）：** AOF 文件越来越大时，Redis 会 fork 子进程把当前内存数据转换为**最少命令集**生成新的 AOF 文件，替换旧文件。比如 100 次 `INCR key` 变成一条 `SET key 100`。

**Redis 4.0 混合持久化：** `aof-use-rdb-preamble yes`，AOF 文件前半部分是 RDB 格式（快速加载），后半部分是 AOF 格式（增量命令）。**兼顾启动速度和数据安全。**

**背诵口诀：** RDB 快照恢复快但可能丢，AOF 日志安全但恢复慢。推荐 everysec + 混合持久化。

> 面试话术：「Redis 持久化有 RDB 和 AOF 两种。RDB 是定期快照，恢复快但可能丢数据；AOF 记录每条写命令，默认每秒刷盘，最多丢 1 秒数据。Redis 4.0 引入混合持久化，AOF 文件前半是 RDB 格式后半是 AOF 命令，兼顾速度和安全。」

## 三、缓存策略
### 4. Redis 的过期策略？

**Redis 对过期 key 的删除策略是：惰性删除 + 定期删除。**

| 策略 | 做什么 | 优缺点 |
|------|--------|--------|
| **惰性删除** | 访问 key 时才检查是否过期，过期则删除 | 省 CPU 但可能大量过期 key 长期占内存 |
| **定期删除** | 每隔一段时间（默认 100ms）**随机抽取**一些设置了过期时间的 key 检查，过期则删除 | 折中方案，但无法保证所有过期 key 都及时清理 |

**为什么不用定时删除？**

定时删除（给每个 key 设一个定时器，到期自动删除）虽然最精确，但**大量定时器会消耗大量 CPU 资源**，影响 Redis 性能。

**惰性 + 定期仍然可能有漏网之鱼怎么办？** → 配合**内存淘汰策略**（下一题）。

**背诵口诀：** 惰性删：用到才查；定期删：随机抽查。两者配合 + 内存淘汰兜底。

> 面试话术：「Redis 使用惰性删除和定期删除两种策略配合。惰性删除在访问 key 时检查是否过期，定期删除每 100ms 随机抽取一批 key 检查。两者都无法保证 100% 清理，所以还需要内存淘汰策略兜底。」
### 5. Redis 的内存淘汰策略？

**当 Redis 内存使用达到 `maxmemory` 上限时，触发内存淘汰。Redis 提供 8 种策略（Redis 4.0+）：**

| 策略 | 范围 | 规则 |
|------|------|------|
| `noeviction`（**默认**） | — | **不淘汰**，新写入直接报错 |
| `allkeys-lru` | 所有 key | 淘汰**最近最少使用**的 key（**最常用**） |
| `allkeys-lfu` | 所有 key | 淘汰**最不经常使用**的 key（Redis 4.0+） |
| `allkeys-random` | 所有 key | 随机淘汰 |
| `volatile-lru` | 设置了过期时间的 key | LRU 淘汰 |
| `volatile-lfu` | 设置了过期时间的 key | LFU 淘汰 |
| `volatile-random` | 设置了过期时间的 key | 随机淘汰 |
| `volatile-ttl` | 设置了过期时间的 key | 淘汰**剩余存活时间最短**的 |

**LRU vs LFU：**
- **LRU**（Least Recently Used）：淘汰最久没被访问的。问题：偶尔一次访问就能续命
- **LFU**（Least Frequently Used）：淘汰访问频率最低的。更准确，但需要额外维护频率计数

**实际推荐：** 缓存场景用 `allkeys-lru` 或 `allkeys-lfu`。

**背诵口诀：** 默认不淘汰会报错，常用 allkeys-lru。LRU 看时间，LFU 看频率。

> 面试话术：「Redis 内存满时有 8 种淘汰策略。默认 noeviction 不淘汰直接报错，缓存场景推荐 allkeys-lru 淘汰最近最少使用的 key。Redis 4.0 新增 LFU 策略基于访问频率，比 LRU 更精准。」

### 6. 什么是缓存穿透、缓存击穿、缓存雪崩？如何解决？

**三种缓存异常场景，都可能导致数据库被打崩：**

| 问题 | 含义 | 原因 |
|------|------|------|
| **缓存穿透** | 请求的数据**缓存和数据库中都不存在** | 恶意攻击或业务 bug，大量请求不存在的 key |
| **缓存击穿** | **热点 key 过期**的瞬间，大量请求打到数据库 | 单个超热 key 过期 |
| **缓存雪崩** | **大量 key 同时过期**或 Redis 宕机，请求全打到数据库 | 批量 key 设了相同过期时间 |

**解决方案：**

| 问题 | 方案 |
|------|------|
| **缓存穿透** | ① **缓存空值**：查不到也缓存一个空值（设短过期时间）<br>② **布隆过滤器**：请求到来时先过布隆过滤器，不存在的直接拒绝 |
| **缓存击穿** | ① **互斥锁**：缓存失效时只让一个线程去查数据库，其他线程等待<br>② **热点 key 永不过期**：后台异步更新缓存 |
| **缓存雪崩** | ① **过期时间加随机值**：避免同时过期<br>② **Redis 集群高可用**：避免单点故障<br>③ **限流降级**：保护数据库 |

**背诵口诀：** 穿透查不到（布隆 + 空值），击穿热 key 崩（加锁 + 永不过期），雪崩一起崩（随机过期 + 集群）。

> 面试话术：「缓存穿透是请求不存在的数据，用布隆过滤器或缓存空值解决。缓存击穿是热点 key 过期瞬间大量请求打到 DB，用互斥锁或永不过期解决。缓存雪崩是大量 key 同时过期，用随机过期时间和 Redis 集群高可用解决。」

### 7. 如何保证缓存和数据库的一致性？

**核心结论：没有强一致方案，只有最终一致。推荐「先更新数据库，再删除缓存」。**

| 方案 | 流程 | 问题 |
|------|------|------|
| ❌ 先更新缓存，再更新 DB | 缓存更新成功，DB 更新失败 → 缓存脏数据 | 不可接受 |
| ❌ 先更新 DB，再更新缓存 | 两个线程同时更新，可能导致缓存和 DB 不一致 | 并发问题 |
| ❌ 先删缓存，再更新 DB | 删完缓存、还没更新 DB 时，另一个请求读到旧数据放入缓存 | **经典脏数据** |
| ✅ **先更新 DB，再删缓存**（Cache Aside） | 更新 DB 成功后删缓存，下次读取时缓存 miss 自动从 DB 加载 | **极小概率**不一致 |

**「先更新 DB，再删缓存」为什么还会有极小概率不一致？**

极端情况：缓存刚好过期 → 线程 A 读 DB 旧值 → 线程 B 更新 DB 新值并删除缓存 → 线程 A 把旧值写入缓存。但这需要**读比写慢**，概率极低。

**兜底方案：**
- **延迟双删**：更新 DB → 删缓存 → **等待一段时间** → **再删一次缓存**
- **消息队列重试**：删缓存失败时发到 MQ，消费者重试删除
- **监听 binlog**：用 Canal 监听 MySQL binlog，自动删除/更新对应缓存

**背诵口诀：** 先更新 DB 再删缓存，删失败用 MQ 重试，终极方案监听 binlog。

> 面试话术：「推荐 Cache Aside 模式：先更新数据库，再删除缓存。删除缓存失败时通过消息队列重试。更可靠的方案是用 Canal 监听 MySQL binlog，自动同步到缓存。注意是删缓存而不是更新缓存，因为懒加载更安全。」

## 四、分布式
### 8. Redis 的分布式锁如何实现？有什么问题？

**Redis 分布式锁的基本实现：用 `SET key value NX PX timeout`。**

```
SET lock_key unique_value NX PX 30000
-- NX：key 不存在才设置（互斥）
-- PX 30000：30 秒自动过期（防止死锁）
-- unique_value：唯一标识（UUID），释放时确认是自己加的锁
```

**释放锁必须用 Lua 脚本保证原子性：**

```lua
-- 先比较 value 是自己的，再删除
if redis.call("get", KEYS[1]) == ARGV[1] then
    return redis.call("del", KEYS[1])
else
    return 0
end
```

**分布式锁的问题：**

| 问题 | 说明 | 解决方案 |
|------|------|---------|
| **超时释放** | 任务未完成但锁过期了，其他线程拿到锁 | **看门狗续期**（Redisson 自动续期，默认 30 秒锁 + 每 10 秒续期） |
| **主从切换** | Master 加锁后还没同步到 Slave 就宕机，Slave 提升为 Master 后没有这把锁 | **RedLock**（向 N 个独立节点加锁，半数以上成功才算加锁成功） |
| **不可重入** | 同一线程重复加锁会失败 | Redisson 支持**可重入锁**（记录线程 ID 和加锁次数） |

**Redisson 框架（生产推荐）：** 封装了看门狗自动续期、可重入、RedLock、公平锁等功能，不需要手动写 Lua 脚本。

**背诵口诀：** SETNX 加锁，Lua 解锁，看门狗续期，RedLock 防主从丢锁。生产用 Redisson。

> 面试话术：「Redis 分布式锁用 SET NX PX 实现，释放时用 Lua 脚本保证原子性。主要问题有：锁超时可以用看门狗续期解决（Redisson）、主从切换丢锁可以用 RedLock 解决。生产环境推荐直接用 Redisson 框架。」

### 9. Redis 的集群模式有哪些？

**Redis 有三种部署模式：主从复制、哨兵模式、Cluster 集群。**

| 模式 | 架构 | 高可用 | 数据分片 |
|------|------|--------|---------|
| **主从复制** | 1 主 N 从，从库复制主库数据 | ❌ 主库挂了需手动切换 | ❌ 不支持 |
| **哨兵模式** | 主从 + Sentinel 监控节点 | ✅ 自动故障转移 | ❌ 不支持 |
| **Cluster** | 多主多从，数据分散在不同节点 | ✅ 自动故障转移 | ✅ **16384 个哈希槽** |

**Redis Cluster 的数据分片：**

- 把所有 key 空间分成 **16384 个槽（slot）**
- 每个 key 通过 `CRC16(key) % 16384` 算出属于哪个槽
- 每个 Master 节点负责一部分槽
- 客户端请求到错误节点时返回 `MOVED` 重定向

**背诵口诀：** 主从只备份，哨兵能自动切，Cluster 能分片。Cluster 16384 个槽，CRC16 取模。

> 面试话术：「Redis 有主从、哨兵和 Cluster 三种模式。主从只做数据备份，故障需手动切换。哨兵在主从基础上增加自动故障转移。Cluster 支持数据分片，用 16384 个哈希槽分配 key，支持水平扩展和自动故障转移。」

### 10. Redis 的哨兵模式原理？

**Sentinel（哨兵）是独立于 Redis 的监控进程，负责：① 监控主从是否正常 ② 自动故障转移 ③ 通知客户端新主库地址。**

**故障转移过程：**
1. **主观下线**：单个 Sentinel 认为 Master 不可用（心跳超时）
2. **客观下线**：**多数 Sentinel**（quorum 个）都认为 Master 不可用
3. **选举 Leader Sentinel**：通过 Raft 算法选出一个 Sentinel 负责执行故障转移
4. **选新 Master**：从 Slave 中选一个提升为 Master（优先级最高、复制偏移量最大、ID 最小）
5. **通知**：让其他 Slave 改为复制新 Master，通知客户端连接新 Master

**建议至少 3 个 Sentinel 节点**，保证投票不会出现平票。

**背诵口诀：** 主观一个说了不算，客观多数才确认。选 Leader 用 Raft，选新 Master 看偏移量。

> 面试话术：「哨兵模式通过多个 Sentinel 节点监控 Redis 主从。当 Master 故障时，先主观下线再客观下线确认，然后选举一个 Sentinel 执行故障转移：从 Slave 中选复制偏移量最大的提升为新 Master，并通知客户端切换连接。」

## 五、高级特性
### 11. Redis 的事务？和关系型数据库的事务有什么区别？

**Redis 事务用 `MULTI`/`EXEC` 实现，但和 MySQL 事务有本质区别：Redis 事务不支持回滚。**

```
MULTI          -- 开启事务
SET key1 v1    -- 命令入队（不立即执行）
SET key2 v2    -- 命令入队
EXEC           -- 一次性执行所有命令
```

| 对比项 | Redis 事务 | MySQL 事务 |
|--------|-----------|-----------|
| 原子性 | ⚠️ 部分原子：命令要么全部入队要么全不入队，但**执行时某条失败不影响其他** | ✅ 全部成功或全部回滚 |
| 回滚 | ❌ **不支持回滚** | ✅ 支持 ROLLBACK |
| 隔离性 | ✅ EXEC 前不会被其他命令打断（单线程） | ✅ 隔离级别保证 |
| 持久性 | 取决于持久化配置 | ✅ WAL 保证 |

**为什么 Redis 不支持回滚？** Redis 作者认为：事务中的错误要么是语法错误（编译时就能发现），要么是类型错误（对 String 执行 List 命令），都是**开发者的 bug**，不应该用回滚来容错。

**WATCH 乐观锁：** `WATCH key` 后如果 key 在 `EXEC` 前被修改，事务自动取消。用于实现 CAS 操作。

**背诵口诀：** Redis 事务不回滚，MULTI 入队 EXEC 执行，WATCH 实现乐观锁。

> 面试话术：「Redis 事务用 MULTI/EXEC 实现，命令入队后一次性执行。和 MySQL 事务最大的区别是不支持回滚——某条命令执行失败不影响其他命令。可以用 WATCH 实现乐观锁，key 被修改则事务取消。」

### 12. Redis 的 Pipeline 和 Lua 脚本？

**Pipeline 和 Lua 脚本都是提升 Redis 性能的手段，但用途不同。**

| 对比项 | Pipeline | Lua 脚本 |
|--------|----------|---------|
| 作用 | **批量发送命令**，减少网络 RTT | **原子执行多条命令**，保证一致性 |
| 原子性 | ❌ 不保证（只是打包发送） | ✅ **原子执行**，中途不会被其他命令打断 |
| 网络优化 | ✅ 多条命令一次网络往返 | ✅ 一次网络往返 |
| 适用场景 | 批量读写，不需要原子性 | 需要原子操作的复杂逻辑（如分布式锁释放） |

**Pipeline 示例效果：** 100 条命令正常需要 100 次网络 RTT，用 Pipeline 只需要 1 次，**性能提升几十倍**。

**Lua 脚本示例（原子性扣库存）：**

```lua
local stock = tonumber(redis.call('GET', KEYS[1]))
if stock > 0 then
    redis.call('DECR', KEYS[1])
    return 1  -- 扣减成功
end
return 0  -- 库存不足
```

整个脚本在 Redis 中**原子执行**，不会出现并发问题。

**背诵口诀：** Pipeline 省网络不保原子，Lua 脚本既省网络又保原子。

> 面试话术：「Pipeline 是把多条命令打包一次发送，减少网络往返次数，但不保证原子性。Lua 脚本在 Redis 中原子执行，适合需要原子性的复杂操作，如分布式锁释放、库存扣减。两者都能减少网络开销。」
