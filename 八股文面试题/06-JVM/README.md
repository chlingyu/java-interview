## 一、内存结构
### 1. JVM 内存结构？各区域的作用？

**JVM 运行时数据区分 5 大块：堆、方法区是线程共享的，虚拟机栈、本地方法栈、程序计数器是线程私有的。** 以下以 HotSpot JVM 为准。

| 区域 | 线程共享 | 存什么 | 异常 |
|------|---------|--------|------|
| **堆（Heap）** | ✅ 共享 | 对象实例、数组 | `OutOfMemoryError` |
| **方法区（Method Area）** | ✅ 共享 | 类信息（Class 元数据）、常量、静态变量、JIT 编译后的代码 | `OutOfMemoryError` |
| **虚拟机栈（VM Stack）** | ❌ 私有 | 栈帧（局部变量表、操作数栈、动态链接、返回地址） | `StackOverflowError` / `OutOfMemoryError` |
| **本地方法栈（Native Method Stack）** | ❌ 私有 | 执行 native 方法时使用的栈 | 同虚拟机栈 |
| **程序计数器（PC Register）** | ❌ 私有 | 当前线程执行的字节码行号 | **唯一不会 OOM 的区域** |

**堆的内部结构（分代模型）：**

```
堆 Heap
├── 新生代（Young Generation）—— 占堆的 1/3
│   ├── Eden 区（占新生代 8/10）
│   ├── Survivor From（占新生代 1/10）
│   └── Survivor To（占新生代 1/10）
└── 老年代（Old Generation）—— 占堆的 2/3
```

- **新生代**：新创建的对象先放 Eden，Minor GC 后存活的对象进入 Survivor，经过 **15 次** GC（默认值，`-XX:MaxTenuringThreshold` 可调）还活着的进入老年代
- **老年代**：存放长期存活的对象、大对象（超过 `-XX:PretenureSizeThreshold` 直接进老年代）

**背诵口诀：** 共享两区堆和方法区，私有三区栈栈计数器。堆分新老，新分 Eden 和两个 Survivor。

> 面试话术：「JVM 运行时数据区分五部分：线程共享的堆和方法区，线程私有的虚拟机栈、本地方法栈和程序计数器。堆用于存放对象实例，按分代模型分为新生代和老年代。方法区存类信息和常量。虚拟机栈每个方法调用创建一个栈帧，存局部变量和操作数。程序计数器是唯一不会 OOM 的区域。」

### 2. 堆和栈的区别？

一句话：**堆存对象，栈存方法调用；堆是共享的慢，栈是私有的快。**

| 对比项 | 堆（Heap） | 栈（VM Stack） |
|--------|-----------|----------------|
| 存什么 | **对象实例和数组** | **局部变量、方法调用信息**（栈帧） |
| 线程共享 | ✅ 所有线程共享 | ❌ 每个线程独立一个栈 |
| 生命周期 | 由 GC 回收，不确定 | 方法结束自动弹栈释放 |
| 大小 | 大（几百 MB~几 GB，`-Xmx` 设置） | 小（默认 512KB~1MB，`-Xss` 设置） |
| 速度 | 相对慢（涉及 GC、锁） | 快（LIFO 入栈出栈，无需 GC） |
| 异常 | `OutOfMemoryError`（对象太多放不下） | `StackOverflowError`（递归太深） |

**这题面试经常挖坑：基本类型变量存在哪？**

- **局部变量**（方法内声明的）：`int a = 10;` → **存在栈上**，值直接在栈帧的局部变量表里
- **成员变量**（对象的字段）：`private int age;` → **存在堆上**，跟着对象走
- **引用类型的局部变量**：`User user = new User();` → 引用 `user` 在**栈上**，User 对象在**堆上**

```java
void foo() {
    int x = 10;              // x 在栈上
    String s = new String(); // s（引用）在栈上，String 对象在堆上
}
```

**背诵口诀：** 堆放对象栈放帧，堆是共享栈私有。局部变量看类型，基本在栈引用在堆。

> 面试话术：「堆存对象实例，线程共享，由 GC 管理；栈存方法调用的局部变量和栈帧，线程私有，方法结束自动释放。基本类型局部变量存在栈上，引用类型的引用在栈上、对象在堆上。」

### 3. 什么是方法区？JDK 1.8 为什么用元空间替代永久代？

**方法区是 JVM 规范定义的逻辑概念，存放类信息、常量、静态变量等。永久代和元空间都是 HotSpot 对方法区的具体实现。**

| 版本 | 方法区实现 | 内存位置 | 特点 |
|------|-----------|---------|------|
| **JDK 7 及之前** | **永久代（PermGen）** | JVM 内存中（和堆连续） | 大小固定（`-XX:MaxPermSize`），容易 OOM |
| **JDK 8+** | **元空间（Metaspace）** | **本地内存（Native Memory）** | 默认不设上限，自动扩展，不容易 OOM |

**为什么要替换？**

1. **永久代容易 OOM**：大小固定，加载的类多了（尤其是 Spring 这种大量动态代理生成类的框架）就报 `OutOfMemoryError: PermGen space`
2. **难以调优**：永久代大小很难提前预估，设小了 OOM，设大了浪费
3. **GC 效率低**：永久代的回收条件苛刻（类的所有实例都被回收 + ClassLoader 被回收 + Class 对象不可达），Full GC 才会清理，效率低
4. **与 JRockit 合并**：Oracle 收购 BEA 后，HotSpot 要和 JRockit 合并，JRockit 本来就没有永久代

**方法区具体存了什么？**

| 内容 | 说明 |
|------|------|
| 类信息 | 类名、父类、接口、字段、方法的字节码 |
| 运行时常量池 | 编译期生成的字面量和符号引用 |
| 静态变量 | `static` 修饰的变量（**JDK 7+ 静态变量引用移到堆中**） |
| JIT 编译代码 | 即时编译器把热点代码编译成的机器码 |

**这题面试经常挖坑：字符串常量池在哪？**

- **JDK 6**：字符串常量池在**永久代**
- **JDK 7+**：字符串常量池移到了**堆**中（`intern()` 放的是引用而不是复制对象）
- 这和方法区/元空间的变化是**两件事**，不要混淆

**背诵口诀：** 永久代固定易炸，元空间本地随便用。字符串常量池 7 进堆，静态变量也跟着走。

> 面试话术：「方法区是 JVM 规范中的逻辑概念，JDK 7 及之前用永久代实现，JDK 8 改用元空间。主要原因是永久代大小固定容易 OOM，元空间使用本地内存，默认不限大小，解决了这个问题。同时 JDK 7 把字符串常量池从永久代移到了堆中。」

### 4. 对象的创建过程？

**HotSpot 中 `new` 一个对象，经历 5 个步骤：类加载检查 → 分配内存 → 零值初始化 → 设置对象头 → 执行 `<init>`。**

| 步骤 | 做什么 | 细节 |
|------|--------|------|
| ① **类加载检查** | 检查类是否已被加载 | 在常量池中找到类的符号引用，检查这个类有没有被加载、解析、初始化过，没有就先走类加载流程 |
| ② **分配内存** | 在堆上划出一块空间 | 两种方式（见下文） |
| ③ **零值初始化** | 给分配的内存设零值 | int→0，boolean→false，引用→null。**这就是为什么成员变量不赋值也有默认值** |
| ④ **设置对象头** | 写入 Mark Word 和类型指针 | 对象的哈希码、GC 分代年龄、锁状态、指向类元数据的指针 |
| ⑤ **执行 `<init>`** | 调用构造方法 | 按代码中的赋值语句和构造方法体进行初始化 |

**内存分配的两种方式：**

| 方式 | 适用场景 | 原理 |
|------|---------|------|
| **指针碰撞（Bump the Pointer）** | 堆内存**规整**（如用 Serial、ParNew 等带压缩的 GC） | 一个指针当分界线，分配时指针往空闲方向移动对象大小的距离 |
| **空闲列表（Free List）** | 堆内存**不规整**（如用 CMS 等不压缩的 GC） | JVM 维护一张表记录哪些内存块可用，分配时找一块够大的 |

**并发分配的线程安全问题：**

多个线程同时 new 对象，指针碰撞可能冲突。HotSpot 的解决方案：

- **TLAB（Thread Local Allocation Buffer）**：每个线程预先在 Eden 区分到一小块专属内存，各自在自己的 TLAB 上分配，互不冲突。TLAB 用完了再通过 CAS + 失败重试同步分配。默认开启（`-XX:+UseTLAB`）。

**背诵口诀：** 加载 → 分配 → 零值 → 头 → init，五步创建一个对象。分配靠碰撞或列表，并发靠 TLAB。

> 面试话术：「HotSpot 中 new 对象分五步：先做类加载检查，然后在堆上分配内存（规整堆用指针碰撞，不规整用空闲列表），接着零值初始化保证默认值，再设置对象头写入元信息，最后执行构造方法。并发分配通过 TLAB 保证线程安全。」

### 5. 对象在内存中的布局？

**HotSpot 中一个对象在堆上的内存布局分三部分：对象头 + 实例数据 + 对齐填充。**

| 部分 | 内容 | 大小（64 位 JVM） |
|------|------|-------------------|
| **对象头（Header）** | Mark Word + 类型指针（+ 数组长度） | 12 字节（开启压缩指针）/ 16 字节 |
| **实例数据（Instance Data）** | 对象的字段值（按分配策略排列） | 取决于字段数量和类型 |
| **对齐填充（Padding）** | 凑整到 **8 字节的整数倍** | 0~7 字节 |

**对象头的结构（重点）：**

| 组成 | 存什么 | 大小 |
|------|--------|------|
| **Mark Word** | **哈希码、GC 分代年龄（4 bit，最大 15）、锁标志位、线程持有的锁、偏向线程 ID** | 8 字节（64 位） |
| **类型指针（Klass Pointer）** | 指向方法区中该类的元数据，JVM 通过它判断对象是哪个类的实例 | 4 字节（压缩）/ 8 字节 |
| **数组长度** | **仅数组对象有**，记录数组长度 | 4 字节 |

**这题面试经常挖坑：Mark Word 在不同锁状态下存的东西不一样**

| 锁状态 | 存储内容 | 标志位 |
|--------|---------|--------|
| 无锁 | 对象 hashCode、GC 年龄 | 01 |
| 偏向锁 | 偏向线程 ID、GC 年龄 | 01 |
| 轻量级锁 | 指向栈中锁记录的指针 | 00 |
| 重量级锁 | 指向 Monitor 的指针 | 10 |
| GC 标记 | 空 | 11 |

**为什么要对齐填充？**

HotSpot 要求对象大小必须是 **8 字节的整数倍**。这是因为 CPU 按 8 字节对齐访问内存效率最高（缓存行对齐）。如果实例数据部分不够 8 的倍数，就用 padding 补齐。

**背诵口诀：** 头 + 数据 + 填充，对齐到 8。Mark Word 最重要：哈希、年龄、锁。

> 面试话术：「对象在内存中分三部分：对象头、实例数据和对齐填充。对象头包含 Mark Word 和类型指针，Mark Word 存了哈希码、GC 年龄、锁状态等信息，不同锁状态下存的内容不同。对齐填充保证对象大小是 8 字节的整数倍，提高 CPU 访问效率。」

## 二、垃圾回收
### 6. 什么是 GC Roots？有哪些？

**GC Roots 是垃圾回收时判断对象是否存活的「根节点」。从 GC Roots 出发，能通过引用链到达的对象就是存活的，到达不了的就是垃圾。** 这叫**可达性分析算法**。

**哪些对象可以作为 GC Roots？**

| GC Root | 说明 |
|---------|------|
| **虚拟机栈中引用的对象** | 方法正在执行时，局部变量表里引用的对象（最常见） |
| **方法区中静态变量引用的对象** | `static` 修饰的引用类型变量 |
| **方法区中常量引用的对象** | `static final` 修饰的引用类型常量 |
| **本地方法栈中 JNI 引用的对象** | native 方法引用的对象 |
| **被 synchronized 锁持有的对象** | 正在被同步的对象 |
| **JVM 内部引用** | 基本类型的 Class 对象、常驻异常（NullPointerException 等）、系统类加载器 |

**背诵口诀：** 栈里的引用、静态变量、常量、native 引用、锁住的对象 —— 五个记住就够用。

**为什么不用引用计数法？**

引用计数法（对象被引用一次计数 +1，引用失效 -1，为 0 就回收）有个致命问题：**循环引用无法回收**。

```java
// 循环引用示例
Object a = new Object();
Object b = new Object();
a.field = b;  // a 引用 b
b.field = a;  // b 引用 a
a = null;
b = null;
// 此时 a、b 互相引用，引用计数都不为 0，但实际已经是垃圾了
```

HotSpot 不使用引用计数法，而是用**可达性分析**，从 GC Roots 出发遍历，避免了循环引用问题。

> 面试话术：「JVM 使用可达性分析算法判断对象是否存活。GC Roots 包括虚拟机栈中的局部变量引用、静态变量引用、常量引用、JNI 引用和被 synchronized 持有的对象。不用引用计数法是因为它无法处理循环引用。」

### 7. 垃圾回收算法有哪些？各有什么优缺点？

**四种核心算法：标记-清除、标记-复制、标记-整理、分代收集。** 实际 JVM 用的是分代收集（组合前三种）。

| 算法 | 原理 | 优点 | 缺点 |
|------|------|------|------|
| **标记-清除** | 先标记所有存活对象，然后清除未标记的 | 简单，不需要移动对象 | **内存碎片**严重；标记和清除效率都不高 |
| **标记-复制** | 内存分两半，只用一半，GC 时把存活对象复制到另一半，清空原来那半 | **没有碎片**，分配快（指针碰撞） | 可用内存只有一半，**浪费空间**；存活对象多时复制开销大 |
| **标记-整理** | 先标记存活对象，然后把它们往一端移动，清理边界外的空间 | **没有碎片**，不浪费空间 | 移动对象有开销，**暂停时间长** |
| **分代收集** | 新生代用**复制算法**，老年代用**标记-清除或标记-整理** | 扬长避短，综合效率最高 | 需要额外维护分代信息 |

**为什么新生代用复制算法？**

新生代里大部分对象都是「朝生夕死」的（IBM 研究表明 98% 的对象活不过第一次 GC），存活率极低。复制算法只需要复制少量存活对象，效率很高。

HotSpot 新生代的具体做法（**Eden : S0 : S1 = 8 : 1 : 1**）：
1. 新对象分配到 Eden
2. Eden 满了触发 Minor GC，存活对象复制到 S0（Survivor From）
3. 下次 GC，Eden + S0 的存活对象复制到 S1，然后 S0 和 S1 角色互换
4. 实际可用空间是 Eden + 一个 Survivor = **90%**，只浪费 10%

**为什么老年代不用复制算法？**

老年代存活率高（都是经过多次 GC 的长寿对象），复制大量对象开销太大。所以用标记-清除（CMS）或标记-整理（Serial Old、Parallel Old）。

**背诵口诀：** 清除有碎片，复制费空间，整理要移动，分代各取所长。新生代朝生夕死用复制，老年代长寿用整理。

> 面试话术：「垃圾回收有四种算法。标记-清除简单但有碎片；标记-复制没碎片但浪费空间；标记-整理没碎片但要移动对象。实际 JVM 用分代收集：新生代对象存活率低，用复制算法效率高；老年代存活率高，用标记-清除或标记-整理。」

### 8. 常见的垃圾回收器有哪些？CMS 和 G1 的区别？

**HotSpot 中有 7 种经典垃圾回收器，分为新生代和老年代两组搭配使用。**

| 回收器 | 代 | 算法 | 线程 | 特点 |
|--------|-----|------|------|------|
| **Serial** | 新生代 | 复制 | 单线程 | 简单高效，Client 模式默认，STW |
| **ParNew** | 新生代 | 复制 | 多线程 | Serial 的多线程版本，**配合 CMS 用** |
| **Parallel Scavenge** | 新生代 | 复制 | 多线程 | 关注**吞吐量**，Server 模式默认（JDK 8） |
| **Serial Old** | 老年代 | 标记-整理 | 单线程 | Serial 的老年代版本 |
| **Parallel Old** | 老年代 | 标记-整理 | 多线程 | 配合 Parallel Scavenge 用 |
| **CMS** | 老年代 | 标记-清除 | 并发 | 关注**最短停顿时间**，JDK 9 标记废弃，JDK 14 移除 |
| **G1** | 整堆 | 标记-整理 + 复制 | 并发 | 面向**大堆低延迟**，JDK 9+ 默认 |

**CMS 的工作流程（四个阶段）：**

| 阶段 | STW | 做什么 |
|------|-----|--------|
| ① 初始标记 | **是** | 只标记 GC Roots 直接关联的对象，速度很快 |
| ② 并发标记 | 否 | 从 GC Roots 出发遍历整个对象图，**和用户线程并发执行** |
| ③ 重新标记 | **是** | 修正并发标记期间用户线程导致的标记变化（增量更新） |
| ④ 并发清除 | 否 | 清除死亡对象，和用户线程并发 |

**CMS 的缺点：**
- **内存碎片**：用标记-清除算法，不整理，碎片多了触发 Full GC 时退化为 Serial Old（单线程整理，卡顿严重）
- **浮动垃圾**：并发清除阶段用户线程产生的新垃圾只能下次 GC 清理
- **CPU 敏感**：并发阶段占用 CPU 资源，影响应用吞吐量
- **Concurrent Mode Failure**：老年代空间不足以容纳新生代晋升的对象时，退化为 Serial Old

**G1 的设计理念：**

G1 打破了传统分代的物理隔离，把堆划分为 **2048 个大小相等的 Region**，每个 Region 可以扮演 Eden、Survivor、Old 或 Humongous（大对象，超过 Region 一半的对象）。

G1 的核心优势是**可预测的停顿时间**：通过 `-XX:MaxGCPauseMillis`（默认 200ms）设定目标停顿时间，G1 会优先回收**垃圾最多的 Region**（Garbage First 的含义），在有限时间内回收最大价值。

**CMS vs G1 对比（高频考点）：**

| 对比项 | CMS | G1 |
|--------|-----|-----|
| 堆模型 | 传统分代（新生代 + 老年代物理隔离） | **Region 模型**（逻辑分代，物理不隔离） |
| 算法 | **标记-清除**（有碎片） | **标记-整理 + 复制**（Region 间复制，无碎片） |
| 内存碎片 | ❌ 严重 | ✅ 每次 GC 都整理，基本无碎片 |
| 停顿控制 | 不可控 | ✅ 通过 `MaxGCPauseMillis` 设置停顿目标 |
| 大对象处理 | 直接进老年代 | **Humongous Region** 专门存放 |
| 适用堆大小 | 几百 MB ~ 几 GB | **6 GB 以上大堆**效果更好 |
| JDK 状态 | JDK 9 废弃，JDK 14 移除 | JDK 9+ 默认回收器 |

**背诵口诀：** CMS 追求低停顿但有碎片，G1 分 Region 可控停顿无碎片。小堆 CMS 够用，大堆选 G1。

> 面试话术：「CMS 关注最短停顿时间，用标记-清除算法，四个阶段只有初始标记和重新标记需要 STW，但缺点是有内存碎片和浮动垃圾。G1 把堆分成 Region 取代传统分代模型，用标记-整理算法没有碎片，可以通过 MaxGCPauseMillis 设置停顿目标，优先回收垃圾最多的 Region，JDK 9 后成为默认回收器。」

### 9. 什么是 Full GC？什么情况下会触发 Full GC？

**Full GC 是对整个堆（新生代 + 老年代）+ 方法区的全面垃圾回收，停顿时间长，是性能调优要尽量避免的。**

| GC 类型 | 回收范围 | 停顿时间 | 频率 |
|---------|---------|---------|------|
| **Minor GC（Young GC）** | 只回收新生代 | 短（ms 级） | 高（Eden 满了就触发） |
| **Major GC** | 只回收老年代（有些资料等同于 Full GC） | 较长 | 较低 |
| **Full GC** | **新生代 + 老年代 + 方法区** | **最长**（可达秒级） | 最低 |

**什么情况会触发 Full GC？（必背）**

| 触发条件 | 说明 |
|---------|------|
| **老年代空间不足** | 大对象直接进老年代、长期存活对象晋升，老年代放不下 |
| **方法区（元空间）不足** | 加载的类太多，元空间满了 |
| **`System.gc()`** | 代码中显式调用，建议 JVM 执行 Full GC（只是建议，不一定执行）。**不要在代码里调** |
| **空间分配担保失败** | Minor GC 前检查：老年代可用空间 < 新生代所有对象大小，且老年代可用空间 < 历次晋升平均大小，担保失败触发 Full GC |
| **CMS Concurrent Mode Failure** | CMS 并发清除时老年代空间不足，退化为 Serial Old 执行 Full GC |
| **JDK 7 永久代空间不足** | JDK 7 及之前永久代满了会触发 Full GC |

**空间分配担保机制（面试追问）：**

Minor GC 之前，JVM 会做以下检查：
1. 老年代可用空间 > 新生代所有对象总大小？→ **安全，直接 Minor GC**
2. 否则，`-XX:HandlePromotionFailure` 允许担保？
   - 允许：老年代可用空间 > 历次晋升到老年代的平均大小？→ **冒险 Minor GC**
   - 不允许或历次平均大小也不够：→ **Full GC**

**如何减少 Full GC？**
- 合理设置新生代、老年代大小比例
- 避免创建过大的对象（大数组、大集合）
- 避免内存泄漏（集合持有对象引用不释放）
- 不要在代码中调用 `System.gc()`
- 选择合适的 GC 回收器（G1 的 Mixed GC 可以减少 Full GC）

**背诵口诀：** Full GC 六大触发：老年代满、方法区满、System.gc()、担保失败、CMS 失败、永久代满。

> 面试话术：「Full GC 是对整个堆和方法区的全面回收，停顿时间最长。触发原因主要有老年代空间不足、方法区满、System.gc() 调用、空间分配担保失败、CMS 的 Concurrent Mode Failure 等。调优的目标就是减少 Full GC 次数。」

## 三、类加载与调优
### 10. 类加载过程？双亲委派模型？

**类加载过程分 5 个阶段：加载 → 验证 → 准备 → 解析 → 初始化。** 其中验证、准备、解析统称为**连接**。

| 阶段 | 做什么 | 细节 |
|------|--------|------|
| ① **加载（Loading）** | 通过类全限定名找到 `.class` 文件，读入字节流，生成 `Class` 对象 | 可以从 jar、网络、动态代理生成等 |
| ② **验证（Verification）** | 检查字节码是否合法、安全 | 文件格式验证（魔数 `CAFEBABE`）、元数据验证、字节码验证、符号引用验证 |
| ③ **准备（Preparation）** | 为**类变量**（static）分配内存并设零值 | `static int a = 10;` → 准备阶段 a = **0**（不是 10！）。但 `static final int a = 10;` → 准备阶段就赋 10（编译期常量直接赋值） |
| ④ **解析（Resolution）** | 把符号引用替换为直接引用 | 如把 `com.example.User` 的符号引用替换为该类在内存中的实际地址 |
| ⑤ **初始化（Initialization）** | 执行 `<clinit>` 方法（类构造器） | 按代码顺序执行 static 变量赋值和 static 代码块。**这时 a 才被赋为 10** |

**这题面试经常挖坑：准备阶段 vs 初始化阶段**

```java
public class Test {
    static int a = 10;         // 准备阶段 a=0，初始化阶段 a=10
    static final int b = 20;   // 准备阶段就是 b=20（编译期常量）
    static final String c = new String("hello"); // 准备阶段 c=null，初始化阶段才赋值（不是编译期常量）
}
```

**双亲委派模型：**

类加载器收到加载请求时，**先委派给父加载器**，父加载器再委派给更上层的，一直到最顶层的 Bootstrap ClassLoader。如果父加载器找不到，才由自己加载。

```
Bootstrap ClassLoader（启动类加载器）—— 加载 rt.jar（java.lang.* 等核心类）
       ↑ 委派
Extension ClassLoader（扩展类加载器）—— 加载 ext 目录下的 jar
       ↑ 委派
Application ClassLoader（应用类加载器）—— 加载 classpath 下的类（我们写的代码）
       ↑ 委派
自定义 ClassLoader
```

**为什么要双亲委派？**

1. **避免类重复加载**：父加载器加载过的类，子加载器不会再加载
2. **保证核心类安全**：防止用户自定义一个 `java.lang.String` 覆盖 JDK 的 String。因为加载 `String` 时一定会委派到 Bootstrap ClassLoader，它只会加载 `rt.jar` 中的 String

**如何打破双亲委派？**

| 方法 | 场景 |
|------|------|
| 重写 `loadClass()` 方法 | 自定义类加载器不先委派给父类 |
| **线程上下文类加载器** | SPI 机制（如 JDBC 的 `DriverManager` 在 rt.jar 中，但具体驱动在 classpath 下，需要反向委托应用类加载器加载） |
| **热部署 / 热替换** | Tomcat 为每个 Web 应用使用独立的类加载器，可以加载同名不同版本的类 |
| **OSGi 模块化** | 网状委派，不是树形 |

**背诵口诀：** 加载验准解初化，五步加载一个类。双亲委派向上找，保证核心不被篡。

> 面试话术：「类加载分五个阶段：加载、验证、准备、解析、初始化。准备阶段给静态变量赋零值，初始化阶段才执行真正的赋值。双亲委派模型让类加载请求先向上委派，保证核心类库不被篡改，同时避免重复加载。JDBC 的 SPI 机制通过线程上下文类加载器打破了双亲委派。」

### 11. 如何排查 OOM 问题？

**OOM（OutOfMemoryError）排查的核心思路：先确定是哪种 OOM，再用工具找到内存泄漏点。**

**常见的 OOM 类型：**

| OOM 类型 | 原因 | 常见场景 |
|----------|------|---------|
| `Java heap space` | **堆内存不足** | 对象太多、内存泄漏、堆设置太小 |
| `Metaspace` / `PermGen space` | 方法区/元空间不足 | 动态生成大量类（如 CGLIB 代理、Groovy 脚本） |
| `GC overhead limit exceeded` | GC 花费 98% 以上时间，回收不到 2% 内存 | 堆太小或内存泄漏 |
| `unable to create new native thread` | 操作系统线程数达上限 | 线程池配置不当、线程泄漏 |
| `Direct buffer memory` | 直接内存（堆外内存）不足 | NIO 的 `ByteBuffer.allocateDirect()` 用太多 |

**排查步骤（实战流程）：**

**第一步：配置 JVM 参数，出事时自动 dump**
```
-XX:+HeapDumpOnOutOfMemoryError
-XX:HeapDumpPath=/path/to/dump.hprof
```
这是**必须提前配好的**，等 OOM 发生时才来配就晚了。

**第二步：用工具分析 dump 文件**

| 工具 | 说明 |
|------|------|
| **MAT（Eclipse Memory Analyzer）** | 最强大的堆内存分析工具，自动生成可疑泄漏报告 |
| **VisualVM** | JDK 自带，轻量级，可以实时监控 + 分析 dump |
| **jhat** | JDK 自带命令行工具，简单查看 dump |
| **Arthas** | 阿里开源，在线诊断，不用重启应用 |

**第三步：定位问题**
- 找到占用内存最多的对象 → 顺着引用链找到持有它的代码
- 常见泄漏原因：
  - `static` 集合不断添加数据不清理
  - 监听器/回调注册后不注销
  - 数据库连接/IO 流没关闭
  - `ThreadLocal` 用完没 `remove()`

**常用命令行工具（面试常问）：**

| 命令 | 作用 |
|------|------|
| `jps` | 列出所有 Java 进程 PID |
| `jstat -gcutil <pid>` | 查看 GC 统计信息（各代使用率、GC 次数和耗时） |
| `jmap -heap <pid>` | 查看堆内存使用情况 |
| `jmap -dump:format=b,file=dump.hprof <pid>` | 手动生成堆 dump 文件 |
| `jstack <pid>` | 查看线程栈（排查死锁、线程阻塞） |
| `jinfo <pid>` | 查看/修改 JVM 参数 |

**背诵口诀：** OOM 排查三步走：提前配 dump 参数 → 用 MAT 分析 → 顺引用链找泄漏。

> 面试话术：「排查 OOM 首先要提前配置 -XX:+HeapDumpOnOutOfMemoryError 保证出事时有现场。然后用 MAT 分析 dump 文件，找到占内存最大的对象，顺着 GC Roots 引用链定位持有者。常见泄漏原因有静态集合不清理、监听器不注销、连接没关闭等。日常可以用 jstat 监控 GC、jmap 看堆、jstack 看线程。」

### 12. JVM 调优参数有哪些？如何调优？

**JVM 调优的核心目标：减少 GC 停顿时间、减少 Full GC 次数、提高吞吐量。调优不是瞎调参数，而是先监控、再分析、最后才改参数。**

**常用 JVM 参数（必背）：**

| 参数 | 作用 | 示例 |
|------|------|------|
| `-Xms` | **堆初始大小**（建议和 Xmx 设成一样，避免动态扩容） | `-Xms2g` |
| `-Xmx` | **堆最大大小** | `-Xmx2g` |
| `-Xmn` | 新生代大小 | `-Xmn512m` |
| `-Xss` | 每个线程的栈大小 | `-Xss256k` |
| `-XX:MetaspaceSize` | 元空间初始大小（触发 Full GC 的阈值） | `-XX:MetaspaceSize=256m` |
| `-XX:MaxMetaspaceSize` | 元空间最大大小 | `-XX:MaxMetaspaceSize=512m` |
| `-XX:NewRatio` | 老年代:新生代 的比值，默认 2（老年代占 2/3） | `-XX:NewRatio=2` |
| `-XX:SurvivorRatio` | Eden:Survivor 的比值，默认 8 | `-XX:SurvivorRatio=8` |
| `-XX:MaxTenuringThreshold` | 对象晋升老年代的年龄阈值，默认 15 | `-XX:MaxTenuringThreshold=15` |
| `-XX:+UseG1GC` | 使用 G1 回收器 | — |
| `-XX:MaxGCPauseMillis` | G1 的目标最大停顿时间 | `-XX:MaxGCPauseMillis=200` |
| `-XX:+HeapDumpOnOutOfMemoryError` | OOM 时自动 dump | — |
| `-XX:+PrintGCDetails` | 打印 GC 详细日志（JDK 8） | — |
| `-Xlog:gc*` | 打印 GC 日志（JDK 9+） | — |

**调优实战步骤：**

| 步骤 | 做什么 | 工具 |
|------|--------|------|
| ① **监控** | 收集 GC 日志，观察 GC 频率、停顿时间、堆使用率 | `jstat`、Prometheus + Grafana、GC 日志 |
| ② **分析** | 找到瓶颈：是 Full GC 太频繁？还是 Young GC 停顿太长？ | GCViewer、GCEasy（在线分析 GC 日志） |
| ③ **调整** | 根据分析结果调参数 | 见下方常见场景 |
| ④ **验证** | 改完后再次观察指标，确认效果 | 同步骤 ① |

**常见调优场景：**

| 问题 | 可能原因 | 调整方案 |
|------|---------|---------|
| **Full GC 频繁** | 老年代太小、大对象太多 | 增大 `-Xmx`；检查是否有内存泄漏 |
| **Young GC 太频繁** | 新生代太小 | 增大 `-Xmn` 或调 `-XX:NewRatio` |
| **GC 停顿太长** | 回收器选择不当 | 换 G1（`-XX:+UseG1GC`）; 调 `-XX:MaxGCPauseMillis` |
| **OOM: Metaspace** | 动态生成类太多 | 增大 `-XX:MaxMetaspaceSize`；检查是否有类加载泄漏 |
| **OOM: heap space** | 堆太小或内存泄漏 | 增大 `-Xmx`；dump 分析找泄漏 |

**这题面试经常挖坑：Xms 和 Xmx 为什么要设成一样？**

如果 Xms < Xmx，JVM 启动时分配 Xms 大小的堆，不够用时动态扩容到 Xmx。**每次扩容都需要申请内存、复制数据，会触发 Full GC**。线上环境设成一样可以避免动态扩容带来的性能抖动。

**背诵口诀：** 先监控后调优，Xms 和 Xmx 设一样，Full GC 多查老年代，Young GC 多扩新生代。

> 面试话术：「JVM 调优核心是减少 Full GC 和控制停顿时间。常用参数有 -Xms/-Xmx 控制堆大小、-Xmn 控制新生代、-XX:+UseG1GC 选择回收器。调优流程是先通过 GC 日志监控现状，分析是 Young GC 还是 Full GC 的问题，然后针对性调参数，最后验证效果。Xms 和 Xmx 建议设成一样避免动态扩容。」
