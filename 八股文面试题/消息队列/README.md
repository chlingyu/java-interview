# 消息队列

---

## 一、基础

### 1. 为什么要用消息队列？

**一句话总结**：消息队列（MQ）的三大核心作用——**解耦**、**异步**、**削峰**。

| 作用 | 说明 | 举例 |
|------|------|------|
| **解耦** | 系统之间不直接调用，通过 MQ 传递消息 | 下单后通知库存、积分、通知等多个系统 |
| **异步** | 非核心操作异步处理，提高响应速度 | 下单成功立即返回，发短信/邮件异步执行 |
| **削峰** | 高并发时消息先堆积在 MQ 中，消费者按能力消费 | 秒杀活动，请求先进 MQ，后端慢慢处理 |

**⚠️ 面试挖坑提醒**：「用 MQ 有什么缺点？」—— ① **系统复杂度增加**（多了一个组件要维护）；② **一致性问题**（消息丢失/重复）；③ **可用性降低**（MQ 挂了怎么办）。

---

### 2. Kafka 的核心架构是怎样的？

**一句话总结**：Kafka 是一个**分布式的发布-订阅消息系统**，核心设计围绕 **Topic（主题）、Partition（分区）、Consumer Group（消费组）、Offset（偏移量）**展开。Kafka 之所以吞吐量极高，靠的是**分区并行、顺序写磁盘、零拷贝、批量发送**。

**核心概念**：

| 概念 | 含义 | 通俗理解 |
|------|------|---------|
| **Topic** | 消息的分类，一个 Topic 就是一个消息队列 | 相当于"频道"，生产者往频道发消息，消费者订阅频道收消息 |
| **Partition** | 一个 Topic 可以分成多个分区，分布在不同 Broker 上 | 一个大队列拆成多个小队列，**并行处理提高吞吐** |
| **Broker** | Kafka 集群中的一个服务器节点 | 一台机器就是一个 Broker |
| **Producer** | 消息生产者，把消息发到指定 Topic 的某个 Partition | — |
| **Consumer Group** | 一组消费者，**组内每个消费者消费不同分区**，组间互不影响 | 同一条消息在组内只被消费一次，不同组各消费一次 |
| **Offset** | 消费者在分区中的消费进度（第几条消息） | 像"书签"，记录读到哪一页了 |
| **Replica（副本）** | 每个 Partition 可以有多个副本，分为 **Leader**（负责读写）和 **Follower**（只负责同步数据） | 主副本干活，其余副本做备份 |
| **ISR（同步副本集合）** | 和 Leader 保持同步的 Replica 集合（In-Sync Replicas） | 只有 ISR 里的副本才有资格被选为新 Leader，**降低数据丢失风险**；真正想尽量不丢，还要配合 `acks=all`、`min.insync.replicas` 等配置 |

**Kafka 为什么快**（面试高频追问）：

| 原因 | 说明 |
|------|------|
| **分区并行** | 多个 Partition 分布在不同 Broker，生产和消费都可以并行 |
| **顺序写磁盘** | 消息追加到日志文件末尾，磁盘顺序写的速度接近内存 |
| **零拷贝（Zero Copy）** | 用 `sendfile` 系统调用直接把数据从磁盘文件发送到网卡，不经过应用层拷贝（详见操作系统相关知识） |
| **批量发送 + 压缩** | 生产者把多条消息攒成一批再发送，减少网络请求次数 |
| **Page Cache** | 利用操作系统的页缓存，热数据直接从内存读取 |

**背诵口诀**：「**Topic 分 Partition 并行跑，Consumer Group 组内分区不重复，Offset 记进度，ISR 保高可用**」

> **面试话术**：Kafka 的核心设计是 Topic 和 Partition。一个 Topic 可以有多个 Partition 分布在不同 Broker 上，实现并行处理。生产者按 key 把消息发到特定 Partition，消费者以 Consumer Group 的方式消费，组内每个消费者负责不同的 Partition，保证同一条消息在组内只被消费一次。每个 Partition 有多个副本，Leader 负责读写，Follower 同步数据，ISR 里的副本随时可以接替 Leader。Kafka 之所以吞吐量极高，主要靠分区并行、顺序写磁盘、零拷贝和批量发送这几个设计。

**⚠️ 面试挖坑提醒**：「Consumer Group 里消费者数量超过 Partition 数会怎样？」—— 多出来的消费者会**空闲**，分不到任何 Partition。所以消费者数量**不要超过 Partition 数**。

### 3. 常见的消息队列有哪些？怎么选？

**一句话总结**：中小公司用 **RabbitMQ**（功能全、文档好），大数据/日志用 **Kafka**（吞吐量高，详见第 2 题），阿里系用 **RocketMQ**（事务消息强）。

| MQ | 语言 | 吞吐量 | 特点 | 适用场景 |
|----|------|--------|------|---------|
| **RabbitMQ** | Erlang | 万级 | 功能全、社区活跃、延迟低 | 中小公司业务系统 |
| **Kafka** | Scala/Java | **百万级** | 吞吐量极高、分布式 | 大数据、日志收集、流处理 |
| **RocketMQ** | Java | 十万级 | 支持**事务消息**、功能丰富 | 电商、金融等对可靠性要求高的场景 |

## 二、可靠性

### 4. 怎么保证消息不丢失？

**一句话总结**：消息可能在**生产者→MQ、MQ 内部、MQ→消费者**三个环节丢失，每个环节都要保证。

| 环节 | 丢失原因 | 解决方案 |
|------|---------|---------|
| **生产者→MQ** | 网络异常发送失败 | **确认机制**（RabbitMQ 的 confirm 模式 / Kafka 的 acks=all） |
| **MQ 内部** | MQ 宕机，消息在内存中没刷盘 | **持久化**（消息持久化到磁盘 + 集群多副本） |
| **MQ→消费者** | 消费者收到消息还没处理就崩了 | **业务处理成功后再确认消费结果**（RabbitMQ 常见是手动 ACK，Kafka 常见是手动提交 offset） |

**背诵口诀**：「**发送确认、存储持久化、消费成功后再确认**」

---

### 5. 怎么保证消息不重复消费（幂等性）？

**一句话总结**：网络重试等原因可能导致消息被消费多次，需要在**消费端做幂等处理**。

**常见幂等方案**：

| 方案 | 原理 |
|------|------|
| **唯一 ID + 去重表** | 每条消息带唯一 ID，消费前查数据库是否已处理过 |
| **数据库唯一约束** | 利用唯一索引防止重复插入 |
| **Redis 的 SETNX** | 用消息 ID 做 key，SETNX 成功才处理 |
| **状态机** | 业务有状态流转时，判断当前状态是否允许操作 |

---

### 6. 怎么保证消息的顺序性？

**一句话总结**：**全局有序很难**（性能差），一般只需保证**局部有序**（同一业务的消息有序）。

| MQ | 实现方式 |
|----|---------|
| **RabbitMQ** | 同一类消息发到**同一个队列**，由**一个消费者**消费 |
| **Kafka** | 同一 key 的消息发到**同一个分区**（Partition），每个分区内有序 |
| **RocketMQ** | 同一业务 ID 的消息发到**同一个队列** |

---

### 7. 什么是死信队列？

**一句话总结**：**死信队列（DLQ，Dead Letter Queue）**存放无法被正常消费的消息，比如消费失败达到最大重试次数、消息过期（TTL 超时）、队列满了被拒绝的消息。

**使用场景**：
- 消费失败多次 → 放入死信队列 → 人工排查或特殊处理
- 实现**延迟队列**：给消息设过期时间（TTL），过期后进入死信队列触发消费

---

### 8. 消息积压了怎么办？

**一句话总结**：消息积压说明**消费者处理速度跟不上生产者**，核心是**提高消费速度**。

**解决方案**：
1. **增加消费者数量**（水平扩展）
2. **排查消费者**是否有慢查询、死锁等问题
3. **临时方案**：新建一个 Topic，用多个消费者把消息快速转移到新 Topic，再扩容后慢慢消费
4. **设置告警**：积压超过阈值自动报警

### 9. RocketMQ 的事务消息是怎么实现的？

**一句话总结**：RocketMQ 通过**半消息（Half Message）+ 两阶段提交 + 事务回查**三个机制，解决「本地事务和消息发送要么同时成功、要么同时失败」的分布式事务问题，实现**最终一致性**。

**为什么需要事务消息**（以电商下单为例）：

用户下单后，需要同时做两件事：① 订单系统创建订单（本地事务）② 通知库存系统扣库存（发 MQ 消息）。问题是：

- 先创建订单再发消息 → 订单成功但消息发失败 → **库存没扣**
- 先发消息再创建订单 → 消息发了但订单创建失败 → **库存扣多了**

两步无论谁先谁后都可能不一致，事务消息就是解决这个问题的。

**RocketMQ 事务消息流程**：

```
生产者                           Broker                        消费者
  |                                |                              |
  |--- ① 发送半消息 -----------→|  存储但标记为「不可投递」       |
  |←-- 半消息发送成功确认 -------|                                |
  |                                |                              |
  |  ② 执行本地事务（如创建订单） |                               |
  |                                |                              |
  |--- ③ 返回事务状态 --------→|                                |
  |    本地事务成功 → Commit      |→ 消息变为可投递 -----------→| 消费者收到消息
  |    本地事务失败 → Rollback    |→ 丢弃半消息（消费者收不到）  |
  |    暂时无法判断 → UNKNOW     |                                |
  |                                |                              |
  |  第③步返回 UNKNOW 或丢失时   |                               |
  |←-- ④ Broker 主动回查 --------|                                |
  |--- 返回本地事务最终状态 ---→|  根据状态 Commit 或 Rollback   |
```

**关键概念**：

| 概念 | 含义 |
|------|------|
| **半消息** | 已发到 Broker 但对消费者**不可见**的消息，等二次确认后才决定投递或丢弃 |
| **二次确认** | 本地事务执行完后，告诉 Broker 这条消息该提交（Commit）、回滚（Rollback）还是暂时无法判断（UNKNOW） |
| **事务回查** | 如果 Broker 收到 UNKNOW，或一段时间内没收到任何二次确认（网络丢了、生产者重启了等），会**主动问生产者**：你的本地事务到底成没成？Broker 会按间隔多次回查，超过上限或超时后默认回滚 |

**⚠️ 面试挖坑提醒**：「事务消息能保证强一致性吗？」—— **不能**，只能保证**最终一致性**。半消息 Commit 后，消费者可能还没消费完，这段时间数据是不一致的。事务消息只能保证**消息最终可投递**，消费成功还要靠**重试 + 幂等 + 死信补偿**兜底（详见本章第 4 题和第 5 题）。强一致性需要分布式事务协议（如两阶段提交 2PC），但性能差很多。

**事务消息 vs 本地消息表**：

| 对比项 | RocketMQ 事务消息 | 本地消息表 |
|--------|-----------------|-----------|
| 原理 | 半消息 + 二次确认 + 回查 | 本地事务中同时写业务表和消息表，定时任务扫描消息表发 MQ |
| 侵入性 | **低**（MQ 原生支持） | 高（要建消息表 + 写定时任务） |
| 实时性 | **高**（秒级） | 低（取决于定时任务扫描间隔） |
| 适用场景 | 用 RocketMQ 的项目首选 | 任何 MQ 都能用，通用性好 |

**背诵口诀**：「**先发半消息，再做本地事务；成功提交失败回滚；丢了就回查**」

> **面试话术**：RocketMQ 事务消息的核心是半消息机制。生产者先发一条半消息到 Broker，这条消息对消费者不可见。然后执行本地事务，成功了就发提交（Commit），Broker 把消息投递给消费者；失败了就发回滚（Rollback），Broker 丢弃这条消息；如果本地事务暂时判断不了，就返回 UNKNOW。Broker 在收到 UNKNOW 或者一直没收到二次确认时，会主动回查生产者的本地事务状态，按间隔多次回查，超时后默认回滚。这样就保证了本地事务和消息发送的最终一致性。和本地消息表方案相比，事务消息侵入性低、实时性高，是用 RocketMQ 的首选方案。
