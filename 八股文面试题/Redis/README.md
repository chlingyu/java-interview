# Redis

---

## 一、基础

### 1. Redis 为什么这么快？

**一句话总结**：Redis 快的原因有 4 个——**基于内存**、**单线程避免上下文切换**、**高效的数据结构**、**IO 多路复用**。

| 原因 | 说明 |
|------|------|
| **基于内存** | 数据存在内存中，读写速度是磁盘的几万倍 |
| **单线程模型** | 避免了多线程的上下文切换和锁竞争开销 |
| **高效数据结构** | 如跳表、压缩列表、哈希表等，专门为性能优化 |
| **IO 多路复用** | 用一个线程监听多个连接的事件（如 epoll），非阻塞处理 |

**⚠️ 面试挖坑提醒**：「Redis 是单线程还是多线程？」—— Redis **核心命令处理**是单线程的。但 Redis 6.0 引入了**多线程 IO**（网络读写用多线程，命令执行仍然单线程），提高网络 IO 性能。

---

### 2. Redis 有哪些常用数据类型？分别用在什么场景？

**一句话总结**：5 种基本类型 + 3 种特殊类型。面试重点答 **5 种基本类型及其场景**。

| 数据类型 | 底层结构 | 典型使用场景 |
|---------|---------|------------|
| **String**（字符串） | SDS（简单动态字符串） | 缓存对象、计数器、分布式锁、Session 共享 |
| **Hash**（哈希） | 哈希表/压缩列表 | 存储对象（如用户信息）、购物车 |
| **List**（列表） | 双向链表/压缩列表 | 消息队列、最新文章列表 |
| **Set**（集合） | 哈希表/整数集合 | 共同关注、抽奖、标签 |
| **Zset**（有序集合） | **跳表** + 哈希表 | **排行榜**、延迟队列 |
| Bitmap | 位数组 | 签到统计、用户在线状态 |
| HyperLogLog | 概率算法 | UV（独立访客）统计 |
| GEO | 有序集合 | 附近的人、门店距离 |

**背诵口诀**：「**String 缓存计数锁，Hash 存对象，List 做队列，Set 去重交并差，Zset 排行榜**」

## 二、持久化

### 3. Redis 的持久化方式有哪些？RDB 和 AOF 有什么区别？

**一句话总结**：RDB 是**定时快照**（全量备份），AOF 是**追加写命令日志**（增量记录）。Redis 4.0+ 支持**混合持久化**。

| 对比项 | RDB | AOF |
|--------|-----|-----|
| 原理 | 某个时间点的**内存快照**（二进制文件） | 记录每条**写命令**（文本文件） |
| 数据安全 | 可能丢失两次快照之间的数据 | 最多丢失 1 秒数据（`everysec` 策略） |
| 文件大小 | **小**（二进制压缩） | **大**（记录每条命令） |
| 恢复速度 | **快** | 慢（需要重放所有命令） |
| 对性能影响 | fork 子进程时短暂阻塞 | `always` 策略影响较大 |

**混合持久化（Redis 4.0+）**：AOF 重写时，前半部分用 RDB 格式存全量数据，后半部分用 AOF 格式存增量命令。**兼顾了 RDB 恢复快和 AOF 数据安全的优点**。

---

### 4. Redis 的过期删除策略是什么？

**一句话总结**：Redis 用**惰性删除 + 定期删除**两种策略配合使用。

| 策略 | 原理 | 特点 |
|------|------|------|
| **惰性删除** | 访问 key 时才检查是否过期，过期就删除 | 对 CPU 友好，但可能有大量过期 key 占内存 |
| **定期删除** | 每秒随机抽取一批过期 key 检查并删除 | 补充惰性删除，减少内存浪费 |

**⚠️ 常见追问**：「如果过期 key 既没有被访问，也没被定期删除扫到，内存满了怎么办？」—— 触发**内存淘汰策略**。

---

### 5. Redis 的内存淘汰策略有哪些？

**一句话总结**：当内存达到上限时，Redis 会按照配置的策略淘汰数据。最常用的是 **`allkeys-lru`**（在所有 key 中淘汰最近最少使用的）。

| 策略 | 说明 |
|------|------|
| `noeviction`（默认） | 不淘汰，新写入直接报错 |
| **`allkeys-lru`** | 在所有 key 中，淘汰**最近最少使用的** |
| `allkeys-lfu` | 在所有 key 中，淘汰**使用频率最低的** |
| `volatile-lru` | 在设了过期时间的 key 中，淘汰最近最少使用的 |
| `volatile-ttl` | 在设了过期时间的 key 中，淘汰**剩余时间最短的** |
| `allkeys-random` | 随机淘汰 |

**背诵口诀**：「**线上推荐 allkeys-lru，兜底不丢用 noeviction**」

## 三、缓存问题

### 6. 什么是缓存穿透、缓存击穿、缓存雪崩？怎么解决？

**一句话总结**：**穿透**是查不存在的数据，**击穿**是热点 key 过期，**雪崩**是大批 key 同时过期或 Redis 宕机。三者都会导致请求直接打到数据库。

| 问题 | 原因 | 解决方案 |
|------|------|---------|
| **缓存穿透** | 查询一个**不存在**的数据（缓存和 DB 都没有） | ① 缓存空值（设短过期时间）② **布隆过滤器**提前拦截 |
| **缓存击穿** | **热点 key** 过期瞬间，大量请求同时打到 DB | ① **互斥锁**（只让一个线程重建缓存）② 设置热点 key 永不过期 |
| **缓存雪崩** | **大批 key 同时过期**或 Redis 宕机 | ① 过期时间加**随机值**分散 ② Redis 集群高可用 ③ 多级缓存 |

**背诵口诀**：「**穿透查空用布隆，击穿热点加互斥，雪崩分散加集群**」

---

### 7. 怎么保证缓存和数据库的一致性？

**一句话总结**：推荐使用**先更新数据库，再删除缓存**（Cache Aside 旁路缓存策略），配合**消息队列重试**保证删除成功。

| 策略 | 做法 | 问题 |
|------|------|------|
| 先更新缓存，再更新 DB | ❌ 不推荐 | 缓存更新成功但 DB 更新失败，数据不一致 |
| 先更新 DB，再更新缓存 | ❌ 不推荐 | 并发场景下可能出现脏数据 |
| **先更新 DB，再删除缓存** | ✅ **推荐** | 极端情况下缓存删除失败 → 用消息队列重试 |

**⚠️ 面试挖坑提醒**：「为什么是删除缓存而不是更新缓存？」—— 因为**更新缓存的代价高**，如果数据频繁修改但很少读取，每次修改都更新缓存是浪费的。删除缓存更简单，下次读取时再从 DB 加载最新数据。

## 四、分布式

### 8. Redis 怎么实现分布式锁？

**一句话总结**：用 `SET key value NX EX timeout` 命令（NX 表示不存在才设置，EX 设置过期时间），释放锁时用 Lua 脚本保证原子性。

```java
// 加锁（NX：不存在才设置，EX：设过期时间防止死锁）
SET lock_key unique_value NX EX 30

// 释放锁（Lua 脚本保证"先判断再删除"的原子性）
if redis.call("get", KEYS[1]) == ARGV[1] then
    return redis.call("del", KEYS[1])
end
```

**⚠️ 面试挖坑提醒**：「简单的 SETNX 有什么问题？」—— 锁过期时间不好设置。如果任务没执行完锁就过期了，其他线程会拿到锁。**Redisson** 框架通过**看门狗（Watchdog）机制**自动续期解决此问题。

### 9. Redis 集群有哪些方案？

**一句话总结**：3 种方案——**主从复制**（读写分离）、**哨兵模式**（自动故障转移）、**Redis Cluster**（数据分片，解决容量瓶颈）。

| 方案 | 解决的问题 | 特点 |
|------|----------|------|
| **主从复制** | 读并发 | 一主多从，主写从读。故障需**手动切换** |
| **哨兵模式** | 高可用 | 在主从基础上加 Sentinel 监控，主挂了**自动切换** |
| **Redis Cluster** | 容量 + 高可用 | 数据分散到多个节点（16384 个哈希槽），**自动分片** |

> **面试话术**：小规模用主从 + 哨兵即可，数据量大了用 Redis Cluster。Cluster 把 16384 个哈希槽分配给多个主节点，每个主节点负责一部分数据，实现水平扩展。每个主节点可以有从节点做高可用。

## 五、高频场景

### 10. Redis 怎么实现消息队列？

**一句话总结**：3 种方式——**List**（简单队列）、**Pub/Sub**（发布订阅）、**Stream**（Redis 5.0 推荐）。

| 方式 | 原理 | 缺点 |
|------|------|------|
| **List** | `LPUSH` 写入 + `BRPOP` 阻塞读取 | 不支持多消费者、消息没有 ACK（确认） |
| **Pub/Sub** | 发布/订阅模式 | 消息不持久化，消费者掉线会丢消息 |
| **Stream** | 类似 Kafka 的消息流 | ✅ 支持消费组、ACK、持久化 |

---

### 11. Redis 的大 Key 问题怎么处理？

**一句话总结**：**大 Key** 是指 value 特别大的 key（如 String 超过 10KB，集合元素超过 5000 个），会导致**网络阻塞**、**操作耗时**、**内存不均**。

**解决方案**：
- **拆分**：把大 Hash 拆成多个小 Hash（按业务维度分 key）
- **压缩**：对 String 类型的 value 进行 GZIP 压缩
- **异步删除**：用 `UNLINK` 代替 `DEL`（后台异步删除，不阻塞主线程）
- **设计规范**：开发时制定 key 的大小规范

---

### 12. Redis 和 Memcached 有什么区别？

**一句话总结**：面试直接说"用 Redis 就对了"。Redis 比 Memcached 多了**持久化、丰富的数据类型、集群支持**。

| 对比项 | Redis | Memcached |
|--------|-------|-----------|
| 数据类型 | **5 种 + 特殊类型** | 只有 String |
| 持久化 | ✅ RDB + AOF | ❌ 不支持 |
| 集群 | ✅ Redis Cluster | 客户端自己分片 |
| 单线程 | ✅ 核心单线程 | 多线程 |
| 适用场景 | **绝大多数场景** | 纯缓存，数据类型简单 |
