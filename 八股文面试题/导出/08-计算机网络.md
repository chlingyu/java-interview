# 计算机网络

---

## 一、网络模型与协议

### 1. TCP/IP 四层模型是什么？

**一句话总结**：TCP/IP 把网络通信分为 **4 层**——应用层、传输层、网络层、网络接口层。每层各司其职，数据从上往下封装，从下往上解封。

| 层 | 功能 | 协议举例 |
|----|------|---------|
| **应用层** | 为用户提供应用服务 | HTTP、HTTPS、DNS、FTP、SMTP |
| **传输层** | 端到端的数据传输 | **TCP**、UDP |
| **网络层** | 路由选择和 IP 寻址 | **IP**、ICMP |
| **网络接口层** | 物理传输 | 以太网、WiFi |

---

### 2. TCP 和 UDP 有什么区别？

**一句话总结**：**TCP** 是面向连接的、可靠的传输（有三次握手、重传机制），**UDP** 是无连接的、不可靠但速度快。

| 对比项 | TCP | UDP |
|--------|-----|-----|
| 连接 | **面向连接**（三次握手） | 无连接 |
| 可靠性 | **可靠**（确认、重传、排序） | 不可靠（可能丢包） |
| 速度 | 相对较慢 | **快** |
| 传输方式 | **字节流** | 数据报 |
| 适用场景 | 文件传输、网页浏览（HTTP） | 视频直播、DNS 查询、游戏 |

---

### 3. TCP 三次握手的过程是怎样的？为什么不是两次？

**一句话总结**：客户端和服务端通过发送 **SYN → SYN+ACK → ACK** 三个报文建立连接。三次握手是为了**确认双方的收发能力都正常**。

```
客户端                   服务端
  |--- SYN(seq=x) -----→|     第一次：客户端发起连接请求
  |←- SYN+ACK(seq=y) ---|     第二次：服务端确认并发起连接
  |--- ACK(seq=x+1) ---→|     第三次：客户端确认
  |====== 连接建立 ======|
```

**为什么不能两次**：
- 两次握手时，服务端无法确认客户端是否**收到了自己的应答**
- 如果网络延迟导致一个**过期的 SYN** 到达服务端，服务端会建立连接等待数据，但客户端并没有真正发起请求，浪费资源

**背诵口诀**：「**一次确认客户端能发，二次确认服务端能收能发，三次确认客户端能收**」

---

### 4. TCP 四次挥手的过程是怎样的？为什么不是三次？

**一句话总结**：断开连接需要 **FIN → ACK → FIN → ACK** 四个报文，因为 TCP 是**全双工**的，两个方向需要分别关闭。

```
客户端                   服务端
  |--- FIN -----------→|     第一次：客户端说"我发完了"
  |←-- ACK ------------|     第二次：服务端说"收到，但我可能还有数据要发"
  |    ... 服务端继续发送剩余数据 ...
  |←-- FIN ------------|     第三次：服务端说"我也发完了"
  |--- ACK -----------→|     第四次：客户端说"收到，连接关闭"
  |== TIME_WAIT 2MSL ==|
```

**为什么不是三次**：因为服务端收到 FIN 后，可能**还有数据没发完**，不能同时发 ACK 和 FIN，所以需要分开。

**⚠️ 面试挖坑提醒**：「客户端最后为什么要等待 2MSL（最长报文寿命的两倍）？」—— ① 确保服务端收到最后的 ACK（如果 ACK 丢了，服务端会重发 FIN）；② 让本次连接的所有报文在网络中消失，避免影响新连接。

### 5. HTTP 和 HTTPS 有什么区别？

**一句话总结**：HTTPS = HTTP + **SSL/TLS 加密**。HTTP 明文传输不安全，HTTPS 加密传输安全。

| 对比项 | HTTP | HTTPS |
|--------|------|-------|
| 端口 | 80 | **443** |
| 安全性 | ❌ 明文传输 | ✅ **加密传输** |
| 证书 | 不需要 | 需要 **SSL/TLS 证书** |
| 性能 | 快 | 略慢（有加密/解密开销） |

---

### 6. HTTP/1.0、HTTP/1.1、HTTP/2、HTTP/3 有什么区别？

**一句话总结**：HTTP 每一代都在解决上一代的性能瓶颈——1.0 短连接浪费、1.1 队头阻塞、2.0 TCP 层队头阻塞、3.0 用 QUIC 协议彻底解决。

| 版本 | 发布年份 | 核心改进 | 仍存在的问题 |
|------|---------|---------|------------|
| **HTTP/1.0** | 1996 | 最基础版本 | **默认短连接**，通常一次请求一个 TCP 连接，用完就断，开销大 |
| **HTTP/1.1** | 1997 | **持久连接**（一个连接可发多个请求）、**管道化** | 有**队头阻塞**：前一个请求没响应，后面的请求只能排队等 |
| **HTTP/2** | 2015 | **多路复用**（一个连接上同时发多个请求互不影响）、**头部压缩**、**服务器推送** | TCP 层仍有**队头阻塞**：一个包丢了会阻塞同一连接的所有流 |
| **HTTP/3** | 2022 | 底层从 TCP 换成 **QUIC（基于 UDP）**，彻底解决队头阻塞 | 部署还不普及 |

**关键概念解释**：

- **持久连接**（HTTP/1.1）：一个 TCP 连接可以发送多个请求，不用每次都重新握手
- **队头阻塞**：前面的请求/响应处理慢了，后面的只能排队。HTTP/1.1 在应用层有这个问题，HTTP/2 用多路复用解决了应用层的问题，但 TCP 层仍然存在（丢包导致整个连接等待重传）
- **多路复用**（HTTP/2）：一个 TCP 连接上可以同时传输多个请求和响应，互不干扰。请求被拆成帧（Frame），不同请求的帧可以交错发送
- **QUIC 协议**（HTTP/3）：基于 UDP 实现的传输协议，内置了 TLS 加密和拥塞控制，每个流独立，**一个流丢包不影响其他流**

**背诵口诀**：「**1.0 一次一连，1.1 长连但排队，2.0 多路复用应用不排了但 TCP 还排，3.0 换 QUIC 彻底不排**」

> **面试话术**：HTTP 的演进主要在解决性能问题。1.0 每次请求都要新建 TCP 连接，1.1 引入持久连接复用 TCP 但有队头阻塞，2.0 用多路复用解决了应用层的队头阻塞并加了头部压缩，但底层 TCP 仍有队头阻塞问题。3.0 把传输层从 TCP 换成了基于 UDP 的 QUIC 协议，每个流独立传输，彻底解决了队头阻塞。

### 7. HTTP 常见的状态码有哪些？

**一句话总结**：状态码分 5 类——1xx 信息，2xx 成功，3xx 重定向，4xx 客户端错误，5xx 服务端错误。

| 状态码 | 含义 | 说明 |
|--------|------|------|
| **200** | OK | 请求成功 |
| **301** | 永久重定向 | 资源永久移到新 URL |
| **302** | 临时重定向 | 资源临时移到新 URL |
| **304** | 未修改 | 资源未改变，可以用缓存 |
| **400** | Bad Request | 请求语法错误 |
| **401** | Unauthorized | 需要认证 |
| **403** | Forbidden | 拒绝访问（有权限问题） |
| **404** | Not Found | 资源不存在 |
| **500** | Internal Server Error | 服务器内部错误 |
| **502** | Bad Gateway | 网关/代理收到了无效响应 |
| **503** | Service Unavailable | 服务暂时不可用 |

### 8. GET 和 POST 有什么区别？

**一句话总结**：**GET** 用于获取资源，参数在 URL 中，**幂等**；**POST** 用于提交数据，参数在请求体中，**不幂等**。

| 对比项 | GET | POST |
|--------|-----|------|
| 用途 | 获取资源 | 提交/修改数据 |
| 参数位置 | URL 中（`?key=value`） | **请求体**中 |
| 安全性 | ❌ 参数暴露在 URL | 相对安全 |
| 幂等性 | ✅ 多次请求结果相同 | ❌ 可能产生不同结果 |
| 长度限制 | 浏览器有 URL 长度限制 | 无限制（理论上） |
| 缓存 | ✅ 可以缓存 | ❌ 不缓存 |

## 二、进阶

### 9. 在浏览器输入 URL 到页面展示，中间发生了什么？

**一句话总结**：**DNS 解析 → TCP 连接 → 发送 HTTP 请求 → 服务器处理 → 返回响应 → 浏览器渲染页面**。

```
1. DNS 解析：把域名转换成 IP 地址
2. TCP 三次握手：建立连接
3. 如果是 HTTPS：还要进行 TLS 握手（协商加密方式）
4. 发送 HTTP 请求
5. 服务器处理请求，返回 HTTP 响应
6. 浏览器解析 HTML/CSS/JS，渲染页面
7. TCP 四次挥手：断开连接
```

### 10. Cookie 和 Session 有什么区别？

**一句话总结**：**Cookie** 存在**客户端**（浏览器），**Session** 存在**服务端**。Session 更安全但占服务器资源。

| 对比项 | Cookie | Session |
|--------|--------|---------|
| 存储位置 | **客户端**（浏览器） | **服务端** |
| 安全性 | ❌ 可以被篡改 | ✅ 更安全 |
| 大小限制 | 4KB | 无限制（受服务器内存限制） |
| 生命周期 | 可设置过期时间 | 浏览器关闭或超时后失效 |
| 常见用法 | 记住登录状态（存 Session ID） | 存储用户会话信息 |

---

### 11. TCP 怎么保证可靠传输？

**一句话总结**：TCP 通过**确认应答、超时重传、滑动窗口、流量控制、拥塞控制**等机制保证数据可靠传输。

| 机制 | 作用 |
|------|------|
| **确认应答（ACK）** | 每收到一段数据就回复 ACK，告诉发送方"我收到了" |
| **超时重传** | 发送后一段时间没收到 ACK，就重新发送 |
| **滑动窗口** | 批量发送多个报文，提高传输效率 |
| **流量控制** | 接收方告诉发送方自己能处理多少数据，防止被淹没 |
| **拥塞控制** | 根据网络状况动态调整发送速率（慢启动 → 拥塞避免 → 快重传 → 快恢复） |
