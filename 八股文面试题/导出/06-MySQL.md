# MySQL

## 一、基础与存储引擎

### 1. InnoDB 和 MyISAM 有什么区别？

**一句话总结**：**InnoDB** 支持事务、行级锁和外键，是 MySQL 5.5+ 的默认引擎；**MyISAM** 不支持事务，只有表级锁，适合读多写少的场景。**面试只需要记 InnoDB**。

| 对比项 | InnoDB | MyISAM |
|--------|--------|--------|
| 事务 | ✅ 支持 | ❌ 不支持 |
| 锁粒度 | **行级锁** | 表级锁 |
| 外键 | ✅ 支持 | ❌ 不支持 |
| 崩溃恢复 | ✅ 通过 Redo Log 恢复 | ❌ |
| 索引类型 | **聚簇索引** | 非聚簇索引 |
| 适用场景 | **绝大多数场景**（默认） | 只读/读多写少 |

**背诵口诀**：「**InnoDB 行锁事务全能，MyISAM 表锁只读能用**」

## 二、索引

### 2. MySQL 索引为什么用 B+ 树？

**一句话总结**：B+ 树**矮胖**（每一层能存很多索引）、**叶子节点有序链表**（方便范围查询）、**非叶子节点不存数据**（一次磁盘读取能加载更多索引），所以适合数据库的磁盘读写场景。

**B+ 树 vs 其他数据结构**：

| 数据结构 | 为什么不用 |
|---------|----------|
| 二叉搜索树 | 可能退化成链表，树太高 |
| 红黑树 | 树高太高，磁盘 IO 次数多 |
| B 树 | 非叶子节点也存数据，每层能放的索引少，树更高 |
| 哈希表 | 不支持**范围查询**和**排序** |

**B+ 树的关键特点**：
- **非叶子节点只存索引**，不存数据 → 一个节点能放更多索引 → 树更矮 → 磁盘 IO 更少
- **叶子节点用双向链表连接** → 范围查询只需顺着链表走，不用再回到根节点
- 一般 3~4 层就能存储**几千万**行数据

> **面试话术**：MySQL 选择 B+ 树主要是因为它适合磁盘存储的场景。B+ 树的非叶子节点只存索引不存数据，所以每个节点能放更多索引，树就更矮，查询时磁盘 IO 次数就更少。另外叶子节点之间用链表连接，范围查询效率很高。

### 3. 什么是聚簇索引和非聚簇索引？什么是回表？

**一句话总结**：**聚簇索引**的叶子节点存的是**完整的行数据**（主键索引就是聚簇索引），**非聚簇索引**（二级索引）的叶子节点存的是**主键值**。通过二级索引查数据时，需要拿到主键再去聚簇索引查完整数据，这个过程叫**回表**。

```
聚簇索引（主键索引）                   二级索引（如 name 索引）
    B+树叶子 → 完整行数据               B+树叶子 → 主键值
    
查询过程（通过 name 查找）：
name 索引找到主键 → 再用主键去聚簇索引找完整数据 = 回表
```

| 概念 | 含义 |
|------|------|
| **聚簇索引** | 主键索引，叶子节点存**完整行数据**，每张表只有一个 |
| **非聚簇索引** | 二级索引（非主键索引），叶子节点存**主键值** |
| **回表** | 通过二级索引查到主键后，再去聚簇索引查完整数据 |
| **覆盖索引** | 查询的字段**全部在索引中**，不需要回表，性能最好 |

**⚠️ 面试挖坑提醒**：「怎么避免回表？」—— 使用**覆盖索引**！让查询所需的字段都包含在索引中，比如 `SELECT id, name FROM user WHERE name = 'Tom'`，如果有 `(name)` 索引，叶子节点存了 name 和 id（主键），不需要回表。

---

### 4. 哪些情况下索引会失效？

**一句话总结**：索引失效就是查询没有走索引而走了**全表扫描**，性能会急剧下降。

**常见索引失效场景**：

| # | 场景 | 示例 | 原因 |
|---|------|------|------|
| 1 | **对索引列使用函数** | `WHERE YEAR(create_time) = 2024` | 函数处理后的值无法匹配索引 |
| 2 | **对索引列做运算** | `WHERE id + 1 = 10` | 同上 |
| 3 | **模糊查询以 % 开头** | `WHERE name LIKE '%Tom'` | 左模糊无法利用索引的有序性 |
| 4 | **隐式类型转换** | `WHERE phone = 13800138000`（phone 是 varchar） | 字符串和数字比较会触发类型转换 |
| 5 | **使用 OR 且其中一列无索引** | `WHERE name = 'Tom' OR age = 18`（age 无索引） | OR 需要两边都走索引才有效 |
| 6 | **违反最左前缀原则** | 联合索引 `(a,b,c)`，查 `WHERE b = 1` | 跳过了最左列 a |
| 7 | **使用 != 或 NOT IN** | `WHERE status != 1` | 否定条件无法有效利用索引 |

**背诵口诀**：「**函数运算左模糊，类型转换 OR 无索引，最左前缀别跳过**」

## 三、事务

### 5. 事务的 ACID 特性是什么？靠什么实现的？

**一句话总结**：事务有 4 大特性 —— 原子性、一致性、隔离性、持久性。InnoDB 通过 **Undo Log、Redo Log、MVCC/锁** 来保证。

| 特性 | 含义 | 实现方式 |
|------|------|---------|
| **原子性（A）** | 事务要么全做，要么全不做 | **Undo Log**（回滚日志） |
| **一致性（C）** | 事务前后数据保持正确 | 由其他三个特性共同保证 |
| **隔离性（I）** | 多个事务之间互不干扰 | **MVCC + 锁** |
| **持久性（D）** | 事务提交后数据永久保存 | **Redo Log**（重做日志） |

**背诵口诀**：「**原子靠 Undo 回滚，持久靠 Redo 重做，隔离靠 MVCC 和锁，一致性靠前三个**」

---

### 6. MySQL 有哪几种事务隔离级别？

**一句话总结**：4 种隔离级别，从低到高：读未提交、读已提交、**可重复读**（MySQL 默认）、串行化。级别越高越安全但性能越差。

| 隔离级别 | 脏读 | 不可重复读 | 幻读 | 说明 |
|---------|------|----------|------|------|
| **读未提交** | ❌ 可能 | ❌ 可能 | ❌ 可能 | 能读到别人没提交的数据 |
| **读已提交** | ✅ 解决 | ❌ 可能 | ❌ 可能 | 只能读到已提交的数据（Oracle 默认） |
| **可重复读** | ✅ 解决 | ✅ 解决 | ❌ 可能* | **MySQL 默认**，同一事务内多次读结果一致 |
| **串行化** | ✅ 解决 | ✅ 解决 | ✅ 解决 | 完全串行，性能最差 |

**三个并发问题**：
- **脏读**：读到了别人**还没提交**的数据（对方可能回滚）
- **不可重复读**：同一事务中两次读**同一行**，结果不一样（对方改了并提交了）
- **幻读**：同一事务中两次查询，**行数变了**（对方插入/删除了）

**⚠️ 面试挖坑提醒**：「MySQL 的可重复读能不能解决幻读？」—— **大部分情况能**！InnoDB 通过 **MVCC**（快照读不会幻读）+ **Next-Key Lock 临键锁**（当前读防止幻读）来解决。但在某些极端场景下仍可能幻读。

---

### 7. 什么是 MVCC？怎么实现的？

**一句话总结**：MVCC（Multi-Version Concurrency Control，多版本并发控制）让**读操作不加锁**，通过维护数据的多个版本，让每个事务看到一个**一致性快照**，从而提高并发性能。

**MVCC 的 3 个核心组件**：

| 组件 | 作用 |
|------|------|
| **隐藏字段** | 每行数据有 `trx_id`（最后修改的事务 ID）和 `roll_pointer`（指向 Undo Log 中的旧版本） |
| **Undo Log 版本链** | 通过 roll_pointer 把同一行数据的所有历史版本串成一条链 |
| **Read View（读视图）** | 事务读取时生成，用于判断"我能看到哪个版本的数据" |

**Read View 判断规则**（简化版）：
- 如果数据的 `trx_id` < 当前最小活跃事务 ID → **看得到**（数据在我之前就提交了）
- 如果数据的 `trx_id` > 当前最大事务 ID → **看不到**（数据是我之后才创建的事务修改的）
- 如果 `trx_id` 在活跃事务列表中 → **看不到**（数据还没提交）

> **面试话术**：MVCC 通过 Undo Log 版本链和 Read View 实现。每行数据有一个事务 ID 和指向旧版本的指针，形成一条版本链。事务读取时生成 Read View，根据事务 ID 判断能看到哪个版本。可重复读级别下，Read View 在事务开始时创建且不变；读已提交级别下，每次读都会重新创建 Read View。

---

### 8. MySQL 有哪些锁？

**一句话总结**：按粒度分为**表锁**和**行锁**；按功能分为**共享锁（读锁）**和**排他锁（写锁）**；InnoDB 的行锁有**记录锁、间隙锁、临键锁**三种。

| 分类方式 | 锁类型 | 说明 |
|---------|--------|------|
| **按粒度** | 表锁 | 锁整张表，粒度大，并发低 |
|  | 行锁 | 锁某一行，粒度小，并发高（InnoDB 特有） |
| **按功能** | 共享锁（S 锁/读锁） | 多个事务可以同时读，`SELECT ... LOCK IN SHARE MODE` |
|  | 排他锁（X 锁/写锁） | 只有一个事务能写，`SELECT ... FOR UPDATE` |
| **InnoDB 行锁** | 记录锁（Record Lock） | 锁定**单条记录** |
|  | 间隙锁（Gap Lock） | 锁定**一个范围**，不含记录本身，防止其他事务在间隙中插入 |
|  | 临键锁（Next-Key Lock） | **记录锁 + 间隙锁**，锁定记录及前面的间隙，是 InnoDB 默认的行锁，用于**防止幻读** |

**⚠️ 面试挖坑提醒**：「InnoDB 的行锁是怎么实现的？」—— InnoDB 的行锁是通过**锁住索引**实现的，不是锁住行本身。如果查询没有走索引，行锁会退化为**表锁**！

## 四、日志

### 9. MySQL 的三大日志是什么？

**一句话总结**：**Undo Log** 保证事务回滚（原子性），**Redo Log** 保证崩溃恢复（持久性），**Binlog** 用于主从复制和数据恢复。

| 日志 | 属于谁 | 作用 | 写入时机 |
|------|--------|------|---------|
| **Undo Log**（回滚日志） | InnoDB 引擎 | 事务回滚 + MVCC 版本链 | 修改数据**之前**写入 |
| **Redo Log**（重做日志） | InnoDB 引擎 | 崩溃恢复，保证已提交的数据不丢失 | 修改数据**之后**写入（先写 Buffer Pool，再刷盘） |
| **Binlog**（归档日志） | MySQL Server 层 | 主从复制 + 数据恢复 | 事务**提交时**写入 |

**⚠️ 面试挖坑提醒**：「Redo Log 和 Binlog 有什么区别？」

| 对比项 | Redo Log | Binlog |
|--------|----------|--------|
| 所属层 | InnoDB 引擎层 | Server 层（所有引擎通用） |
| 内容 | **物理日志**（哪个数据页做了什么修改） | **逻辑日志**（SQL 语句或行变更） |
| 大小 | 固定大小，循环写（写满了会覆盖） | 追加写（不会覆盖，可以归档） |
| 用途 | 崩溃恢复 | 主从复制 + 数据恢复 |

---

### 10. 什么是 Buffer Pool？为什么需要它？

**一句话总结**：Buffer Pool（缓冲池）是 InnoDB 在**内存中**开辟的一块区域，用来**缓存磁盘上的数据页和索引页**。读数据时先从 Buffer Pool 找，写数据时也是先改 Buffer Pool 中的页（此时叫**脏页**），再择机刷回磁盘，从而大幅减少磁盘 IO。

**为什么需要 Buffer Pool**：数据库的瓶颈在磁盘 IO。如果每次读写都直接操作磁盘，性能会非常差。Buffer Pool 让**热数据常驻内存**，把随机磁盘读写转化为内存操作，是 InnoDB 高性能的核心。

**Buffer Pool 的工作流程**：

```
读数据：先查 Buffer Pool → 命中直接返回（快）→ 未命中则从磁盘加载到 Buffer Pool 再返回
写数据：先改 Buffer Pool 中的页（变成脏页）→ 同时写 Redo Log（详见第 9 题）→ 后台线程择机把脏页刷回磁盘
```

**Buffer Pool 中的关键机制**：

| 机制 | 作用 |
|------|------|
| **脏页（Dirty Page）** | Buffer Pool 中被修改但还没刷回磁盘的页。崩溃后通过 **Redo Log** 重放已提交但未刷盘的修改 |
| **最近最少使用（LRU）链表** | 管理页的淘汰，按“最近访问时间”决定哪些页被淘汰。InnoDB 用**改进版 LRU**（分为 young 区和 old 区），防止全表扫描等一次性操作把热数据挤出去 |
| **Flush 链表** | 记录哪些是脏页，后台线程按这个链表把脏页刷回磁盘 |
| **预读（Read Ahead）** | 预判即将访问的相邻数据页，提前加载到 Buffer Pool |

**⚠️ 面试挖坑提醒**：「Buffer Pool 的大小怎么设置？」—— 通过 `innodb_buffer_pool_size` 参数设置，**生产环境一般设为物理内存的 60%~80%**。Buffer Pool 太小会频繁淘汰热数据导致磁盘 IO 增加；太大会挤占操作系统和其他进程的内存。

> **面试话术**：Buffer Pool 是 InnoDB 在内存中缓存数据页和索引页的区域，是 InnoDB 高性能的核心。读数据时优先从 Buffer Pool 找，避免磁盘 IO；写数据时先改 Buffer Pool 里的页变成脏页，同时写 Redo Log 保证持久性，再由后台线程择机把脏页刷回磁盘。Buffer Pool 用改进版的 LRU 算法管理页的淘汰，防止全表扫描把热数据挤出去。

**关联知识点**：第 9 题中 Redo Log 的"先写 Buffer Pool，再刷盘"就是指这个流程。Buffer Pool 是**内存层面的缓存**，Redo Log 是**崩溃恢复的保障**，两者配合实现了高性能 + 高可靠。

### 11. 什么是两阶段提交？为什么需要它？

**一句话总结**：两阶段提交（Two-Phase Commit，2PC）是 InnoDB 用来保证 **Redo Log 和 Binlog 数据一致**的机制。事务提交时先写 Redo Log（prepare 状态）→ 再写 Binlog → 最后把 Redo Log 改为 commit 状态，确保崩溃恢复后两份日志不会矛盾。

**为什么需要两阶段提交**：因为 Redo Log（InnoDB 引擎层）和 Binlog（Server 层）是**两个独立的日志**，如果不协调就可能出现不一致：

| 故障场景 | 不用两阶段提交会怎样 |
|---------|-------------------|
| 写完 Redo Log 后崩溃，Binlog 没写 | 主库通过 Redo Log 恢复了数据，但从库没收到 Binlog → **主从不一致** |
| 写完 Binlog 后崩溃，Redo Log 没提交 | 从库通过 Binlog 同步了数据，但主库没有这条数据 → **主从不一致** |

**两阶段提交的流程**：

```
事务执行（修改 Buffer Pool 中的数据页）
    │
    ▼
① 写 Redo Log，标记为 prepare 状态
    │
    ▼
② 写 Binlog
    │
    ▼
③ 把 Redo Log 标记为 commit 状态 → 事务提交完成
```

**崩溃恢复时的判断逻辑**：

| Redo Log 状态 | Binlog 中能否找到该事务的完整 XID | 恢复决策 |
|-------------|---------------|---------|
| prepare | ✅ 在 Binlog 中找到该事务对应的完整 XID | **提交事务**（Binlog 已写，从库可能已同步） |
| prepare | ❌ 在 Binlog 中找不到完整的事务事件 | **回滚事务**（Binlog 没写完，当作没发生） |
| commit | — | **提交事务**（正常完成的事务） |

**背诵口诀**：「**先 prepare 再 binlog 最后 commit，两个日志要么都有要么都没有**」

> **面试话术**：两阶段提交是为了保证 Redo Log 和 Binlog 的一致性。事务提交分三步：先写 Redo Log 标记为 prepare，再写 Binlog，最后把 Redo Log 改为 commit。如果中间崩溃了，恢复时先看 Redo Log 是不是 prepare 状态，如果是就再看 Binlog 中能不能找到该事务对应的完整 XID——找得到就提交，找不到就回滚。Binlog 是崩溃恢复阶段的事实来源，保证两份日志要么都有这条事务，要么都没有，不会出现主从不一致的问题。

**⚠️ 面试挖坑提醒**：「两阶段提交有什么性能问题？」—— 在高可靠配置下（`innodb_flush_log_at_trx_commit=1` 且 `sync_binlog=1`），每次事务提交都要刷盘两次（Redo Log + Binlog），IO 压力大。MySQL 5.6 引入了**组提交（Group Commit）**优化：把多个事务的日志合并在一起刷盘，减少磁盘 IO 次数，显著提升高并发场景的性能。

## 五、SQL 优化

### 12. 怎么用 Explain 分析 SQL？

**一句话总结**：在 SQL 语句前加 `EXPLAIN`，可以查看查询的**执行计划**，重点关注 `type`（访问类型）和 `key`（用了哪个索引）。

**Explain 最重要的几个字段**：

| 字段 | 含义 | 关注点 |
|------|------|--------|
| **type** | 访问类型（性能从好到差） | `const` > `eq_ref` > `ref` > `range` > `index` > **`ALL`（全表扫描，要优化！）** |
| **key** | 实际使用的索引 | 如果是 NULL 说明没走索引 |
| **rows** | 预估扫描行数 | 越小越好 |
| **Extra** | 额外信息 | `Using index`（覆盖索引，好）、`Using filesort`（额外排序，差）、`Using temporary`（临时表，差） |

---

### 13. 怎么优化慢 SQL？

**一句话总结**：先用**慢查询日志**找到慢 SQL → 用 **Explain 分析**执行计划 → **针对性优化**。

**常见优化手段**：

| # | 优化方式 | 说明 |
|---|---------|------|
| 1 | **加索引** | 针对 WHERE、JOIN、ORDER BY 的列建索引 |
| 2 | **避免 SELECT *** | 只查需要的字段，减少数据传输 |
| 3 | **用覆盖索引** | 让查询字段都在索引中，避免回表 |
| 4 | **优化分页** | `LIMIT 100000, 10` 改为先用子查询定位 id 再分页 |
| 5 | **避免索引失效** | 参考第 4 题的失效场景 |
| 6 | **用 JOIN 代替子查询** | 子查询可能产生临时表，JOIN 通常更快 |
| 7 | **合理使用联合索引** | 遵循最左前缀原则 |

---

### 14. 什么是最左前缀原则？

**一句话总结**：联合索引 `(a, b, c)` 必须**从最左边的列开始匹配**，不能跳过左边的列。

| 查询条件 | 是否走索引 | 说明 |
|---------|----------|------|
| `WHERE a = 1` | ✅ | 匹配最左列 |
| `WHERE a = 1 AND b = 2` | ✅ | 匹配前两列 |
| `WHERE a = 1 AND b = 2 AND c = 3` | ✅ | 全部匹配 |
| `WHERE b = 2` | ❌ | 跳过了 a |
| `WHERE a = 1 AND c = 3` | ⚠️ 部分 | 只走 a 的索引，c 不走索引 |

---

### 15. 什么是分库分表？什么时候需要？

**一句话总结**：当单表数据量太大（一般超过 **500 万行**或单表超过 **2GB**），查询性能严重下降时，需要把数据拆分到多个库或表中。

| 方式 | 说明 | 适用场景 |
|------|------|---------|
| **垂直分表** | 把一张表的**列**拆到不同表中 | 字段太多，热门字段和冷门字段分开 |
| **水平分表** | 把一张表的**行**拆到多张结构相同的表中 | 数据量太大，如按用户 ID 取模分表 |
| **分库** | 把不同的表放到不同的数据库实例中 | 数据库连接数或 IO 瓶颈 |

**⚠️ 面试挖坑提醒**：「分库分表后会带来什么问题？」—— 分布式事务、跨表 JOIN、全局 ID 生成（雪花算法）、数据迁移等。所以**能不分就不分**，先试试优化索引和读写分离。

### 16. MySQL 主从复制的原理是什么？

**一句话总结**：主库把数据变更写入 **Binlog** → 从库的 IO 线程拉取 Binlog 写入**中继日志（Relay Log）**→ 从库的 SQL 线程重放中继日志完成同步。

```
主库（Master）                    从库（Slave）
写操作 → Binlog → ─────────→ IO 线程 → Relay Log → SQL 线程 → 同步数据
```

**主从复制的用途**：
- **读写分离**：主库写，从库读，分担压力
- **数据备份**：从库作为热备份
- **高可用**：主库故障时从库可以切换为主库

---

### 17. MySQL 的 Binlog 有哪几种格式？

**一句话总结**：3 种格式 —— **Statement**（记 SQL 语句）、**Row**（记行变更）、**Mixed**（混合）。推荐用 **Row** 格式。

| 格式 | 记录内容 | 优点 | 缺点 |
|------|---------|------|------|
| **Statement** | SQL 语句原文 | 日志量小 | 某些函数（如 `NOW()`）主从不一致 |
| **Row** | 每行数据的变更 | **数据一致性最好** | 日志量大 |
| **Mixed** | 默认用 Statement，不安全时自动切 Row | 折中方案 | 不够统一 |
