## 一、存储引擎
### 1. InnoDB 和 MyISAM 的区别？

一句话：**InnoDB 支持事务和行锁，MyISAM 不支持事务只有表锁。MySQL 5.5+ 默认 InnoDB，绝大多数场景用 InnoDB。**

| 对比项 | InnoDB | MyISAM |
|--------|--------|--------|
| 事务 | ✅ 支持（ACID） | ❌ 不支持 |
| 锁粒度 | **行锁**（并发高） | **表锁**（并发低） |
| 外键 | ✅ 支持 | ❌ 不支持 |
| 崩溃恢复 | ✅ 通过 **redo log** 实现崩溃恢复 | ❌ 崩溃后容易损坏 |
| 索引结构 | **聚簇索引**（数据和索引存在一起） | **非聚簇索引**（数据和索引分开存） |
| 全文索引 | MySQL 5.6+ 支持 | ✅ 支持 |
| 存储文件 | `.ibd`（数据+索引） | `.MYD`（数据）+ `.MYI`（索引） |
| `count(*)` | 需要遍历（因为 MVCC 不同事务看到的行数不同） | 直接返回（有变量记录行数） |

**什么时候用 MyISAM？** 几乎不用了。只有**只读或读多写少、不需要事务**的历史遗留系统可能还在用。

**背诵口诀：** InnoDB 事务行锁聚簇索引，MyISAM 无事务表锁非聚簇。

> 面试话术：「InnoDB 支持事务、行锁和外键，使用聚簇索引，通过 redo log 实现崩溃恢复，是 MySQL 5.5+ 的默认引擎。MyISAM 不支持事务，只有表锁，并发性能差。现在几乎都用 InnoDB。」

## 二、索引
### 2. MySQL 的索引类型有哪些？

**从不同维度分类：**

| 维度 | 类型 | 说明 |
|------|------|------|
| **数据结构** | B+ 树索引 | **最常用**，InnoDB 默认 |
| | Hash 索引 | Memory 引擎支持，等值查询 O(1) 但不支持范围查询 |
| | 全文索引 | `FULLTEXT`，用于全文搜索 |
| **物理存储** | 聚簇索引 | 叶子节点存**整行数据**，InnoDB 主键索引就是聚簇索引 |
| | 非聚簇索引（二级索引） | 叶子节点存**主键值**，查数据要**回表** |
| **逻辑功能** | 主键索引 | `PRIMARY KEY`，唯一且非空 |
| | 唯一索引 | `UNIQUE`，值唯一但允许 NULL |
| | 普通索引 | `INDEX`，无约束 |
| | 联合索引（组合索引） | 多列组合，遵循**最左前缀原则** |

**联合索引的最左前缀原则：**

联合索引 `(a, b, c)` 相当于创建了 `(a)`、`(a, b)`、`(a, b, c)` 三个索引。查询条件必须从最左列开始才能用到索引：
- `WHERE a = 1 AND b = 2` ✅ 走索引
- `WHERE b = 2 AND c = 3` ❌ 不走索引（跳过了 a）
- `WHERE a = 1 AND c = 3` ⚠️ 只用到 a 部分

**背诵口诀：** B+ 树最常用，聚簇存数据二级存主键，联合索引最左前缀。

> 面试话术：「MySQL 索引按数据结构分有 B+ 树、Hash、全文索引；按存储分有聚簇和非聚簇索引；按功能分有主键、唯一、普通和联合索引。InnoDB 的主键索引是聚簇索引，二级索引叶子存主键需要回表。联合索引遵循最左前缀原则。」

### 3. B+ 树和 B 树的区别？为什么 MySQL 用 B+ 树？

**B+ 树和 B 树的核心区别：B+ 树数据只存在叶子节点，叶子节点之间有指针串成链表。**

| 对比项 | B 树 | B+ 树 |
|--------|------|-------|
| 数据存储 | 数据分散在**所有节点** | 数据**只在叶子节点** |
| 叶子节点链表 | 无 | 叶子节点通过**双向链表**连接 |
| 非叶子节点 | 存 key + data | **只存 key**（索引指针） |
| 查询稳定性 | 不稳定（可能在中间节点就找到） | ✅ **稳定**，所有查询都到叶子节点，IO 次数一致 |
| 范围查询 | 需要中序遍历整棵树 | ✅ 叶子链表顺序扫描，**极快** |

**为什么 MySQL 选择 B+ 树？**

1. **磁盘 IO 少**：非叶子节点只存 key 不存 data，一个节点（一页 16KB）能放更多 key，**树更矮**。InnoDB 中 3 层 B+ 树就能存约 **2000 万行**数据，只需要 3 次磁盘 IO
2. **范围查询高效**：叶子节点双向链表串联，`BETWEEN`、`ORDER BY`、`>`、`<` 只需要顺序扫描链表
3. **查询性能稳定**：每次查询都走到叶子节点，IO 次数固定（等于树的高度）

**这题面试经常挖坑：为什么不用 Hash 索引？**

Hash 索引等值查询 O(1) 很快，但**不支持范围查询、排序、最左前缀**。数据库操作大量涉及范围扫描，所以 B+ 树是更好的选择。

**背诵口诀：** B+ 树三大优势：树矮 IO 少，链表范围查，性能稳定走叶子。

> 面试话术：「B+ 树和 B 树的区别是 B+ 树数据只存叶子节点，叶子之间有双向链表。MySQL 用 B+ 树是因为：非叶子节点不存数据能放更多 key，树更矮 IO 更少；叶子节点链表支持高效范围查询；所有查询都到叶子节点，性能稳定。3 层 B+ 树就能存约 2000 万行数据。」

### 4. 聚簇索引和非聚簇索引的区别？

一句话：**聚簇索引的叶子节点存整行数据，非聚簇索引的叶子节点存主键值。**

| 对比项 | 聚簇索引 | 非聚簇索引（二级索引） |
|--------|---------|---------------------|
| 叶子节点存什么 | **整行数据** | **主键值** |
| 一张表有几个 | **只能有一个** | 可以有多个 |
| 谁是聚簇索引 | 主键索引（没主键就用唯一索引，都没有就用隐藏的 `ROW_ID`） | 除主键外的其他索引 |
| 查询性能 | 直接拿到数据，**不用回表** | 先查到主键，再根据主键去聚簇索引**回表**查数据 |

**什么是回表？**

用非聚簇索引查询时，叶子节点只有主键值，还需要**拿着主键去聚簇索引再查一次**才能拿到完整数据，这个过程叫**回表**。

```sql
-- 假设 name 上有普通索引
SELECT * FROM user WHERE name = '张三';
-- 1. 先在 name 索引树找到主键 id=5
-- 2. 再用 id=5 去聚簇索引树找到整行数据 → 这就是回表
```

**如何避免回表？→ 覆盖索引**

如果查询的列**都在索引中**，就不需要回表了。比如联合索引 `(name, age)` 查 `SELECT name, age FROM user WHERE name = '张三'`，索引叶子节点已经包含 name 和 age，直接返回，不用去聚簇索引。

**这题面试经常挖坑：InnoDB 为什么必须有主键？**

因为 InnoDB 是按聚簇索引组织数据的，**数据必须挂在聚簇索引树上**。如果没有主键，InnoDB 会找一个唯一非空索引当聚簇索引；如果也没有，就自动生成一个 6 字节的隐藏列 `ROW_ID`。所以建表时**一定要有主键**，且最好用**自增 ID**（插入时顺序追加，不会导致页分裂）。

**背诵口诀：** 聚簇存数据只一个，二级存主键要回表。覆盖索引免回表，主键自增少分裂。

> 面试话术：「聚簇索引叶子节点存整行数据，一张表只有一个，InnoDB 的主键索引就是聚簇索引。非聚簇索引叶子存主键值，查询时需要回表。可以通过覆盖索引避免回表——查询列都在索引中就不需要再去聚簇索引了。InnoDB 必须有主键，推荐自增 ID 避免页分裂。」

### 5. 什么是覆盖索引？什么是索引下推？

**覆盖索引：** 查询的列**全部包含在索引中**，不需要回表查聚簇索引。`EXPLAIN` 中 Extra 列显示 `Using index` 就是用了覆盖索引。

```sql
-- 联合索引 (name, age)
SELECT name, age FROM user WHERE name = '张三'; -- ✅ 覆盖索引，不回表
SELECT name, age, email FROM user WHERE name = '张三'; -- ❌ email 不在索引中，需要回表
```

**索引下推（IPC，Index Condition Pushdown，MySQL 5.6+）：** 在索引遍历过程中，**先用索引中的列过滤**不满足条件的行，减少回表次数。`EXPLAIN` 中 Extra 列显示 `Using index condition`。

```sql
-- 联合索引 (name, age)
SELECT * FROM user WHERE name LIKE '张%' AND age = 25;
-- 没有索引下推：用 name 索引找到所有"张%"的行 → 全部回表 → 再逐行检查 age=25
-- 有索引下推：用 name 索引找到"张%"的行 → 在索引中直接检查 age=25 → 只对满足条件的回表
```

**背诵口诀：** 覆盖索引不回表（Using index），索引下推少回表（Using index condition）。

> 面试话术：「覆盖索引是查询列都在索引中，不需要回表，性能最好。索引下推是 MySQL 5.6 引入的优化，在索引遍历时提前用索引中的列过滤数据，减少不必要的回表次数。」

### 6. 什么情况下索引会失效？

**索引失效的常见场景（必背）：**

| 场景 | 示例 | 原因 |
|------|------|------|
| **对索引列用函数/计算** | `WHERE YEAR(create_time) = 2024` | 函数破坏了 B+ 树的有序性 |
| **隐式类型转换** | `WHERE phone = 13800138000`（phone 是 varchar） | 数据库对 phone 做了隐式 `CAST`，等于加了函数 |
| **LIKE 以 % 开头** | `WHERE name LIKE '%三'` | B+ 树按前缀排序，% 开头无法定位 |
| **OR 中有非索引列** | `WHERE name = '张三' OR email = 'x'`（email 无索引） | 有一个条件用不了索引就全表扫描 |
| **不满足最左前缀** | 联合索引 `(a, b, c)`，`WHERE b = 1` | 跳过了最左列 a |
| **IS NULL / IS NOT NULL**（看情况） | `WHERE name IS NOT NULL` | 优化器判断数据量大时不走索引 |
| **NOT IN / !=** | `WHERE status != 1` | 优化器可能认为全表扫描更快 |
| **数据量小** | 表只有几十行 | 优化器判断全表扫描比走索引更快 |

**这题面试经常挖坑：索引失效不是绝对的！**

最终是否走索引由 MySQL **优化器**决定，它会评估走索引 vs 全表扫描的成本。如果优化器认为大部分行都满足条件（如 `status != 1` 但 99% 的行 status 都不是 1），全表扫描更快，就不走索引。

**如何排查索引是否生效？** 用 `EXPLAIN` 看 `type` 列和 `key` 列。

**背诵口诀：** 函数计算和转换，LIKE 百分号在前，OR 混非索引，最左前缀没遵守——这些都会让索引失效。

> 面试话术：「索引失效常见场景有：对索引列使用函数或计算、隐式类型转换、LIKE 以 % 开头、OR 中有非索引列、不满足最左前缀原则。但是否走索引最终由优化器决定，用 EXPLAIN 可以确认执行计划。」

## 三、事务与锁
### 7. MySQL 的事务隔离级别？各有什么问题？

**MySQL（InnoDB）支持四种事务隔离级别，默认是 `REPEATABLE READ`（可重复读）。**

| 隔离级别 | 脏读 | 不可重复读 | 幻读 |
|---------|------|-----------|------|
| **READ UNCOMMITTED**（读未提交） | ⚠️ 可能 | ⚠️ 可能 | ⚠️ 可能 |
| **READ COMMITTED**（读已提交） | ✅ 解决 | ⚠️ 可能 | ⚠️ 可能 |
| **REPEATABLE READ**（可重复读，**InnoDB 默认**） | ✅ 解决 | ✅ 解决 | ✅ InnoDB 通过 MVCC + 间隙锁**基本解决** |
| **SERIALIZABLE**（串行化） | ✅ 解决 | ✅ 解决 | ✅ 解决（但**性能最差**） |

**三种读问题是什么？**

| 问题 | 含义 | 举例 |
|------|------|------|
| **脏读** | 读到其他事务**未提交**的数据 | 事务 A 修改了一行但没提交，事务 B 读到了，A 回滚了，B 读到的就是「脏」数据 |
| **不可重复读** | 同一事务中**两次读同一行**结果不同 | 事务 A 第一次读 age=20，事务 B 把 age 改成 25 并提交，事务 A 第二次读 age=25 |
| **幻读** | 同一事务中**两次查询行数不同**（多了或少了行） | 事务 A 查到 10 条记录，事务 B 插入 1 条并提交，事务 A 再查变 11 条 |

**这题面试经常挖坑：InnoDB 的 RR 级别真的能防幻读吗？**

**大部分场景能，但不是完全防住。** InnoDB 在 RR 级别下通过两种方式防幻读：
- **MVCC（快照读）**：普通 SELECT 读的是事务开始时的快照，看不到其他事务的修改
- **间隙锁（当前读）**：`SELECT ... FOR UPDATE` 等当前读操作会加间隙锁，阻止其他事务在范围内插入

但在某些极端场景（如先快照读再当前读）仍可能出现幻读。

**背诵口诀：** 读未提交啥都漏，读已提交防脏读，可重复读防两读，串行化全防但最慢。InnoDB 默认 RR + MVCC + 间隙锁。

> 面试话术：「MySQL 有四种隔离级别，InnoDB 默认可重复读。脏读是读到未提交数据，不可重复读是两次读同一行结果不同，幻读是两次查询行数不同。InnoDB 在 RR 级别下通过 MVCC 解决快照读的幻读，通过间隙锁解决当前读的幻读。」

### 8. MVCC 的实现原理？

**MVCC（多版本并发控制）是 InnoDB 实现 RC 和 RR 隔离级别的核心机制，让读写不加锁也能保证一致性。** 核心思想是**每行数据保存多个版本，事务根据时间点读取对应版本**。

**MVCC 三大组件：**

| 组件 | 作用 |
|------|------|
| **隐藏列** | 每行数据有两个隐藏字段：`DB_TRX_ID`（最后修改该行的事务 ID）、`DB_ROLL_PTR`（指向 undo log 的指针） |
| **undo log（版本链）** | 每次修改生成旧版本数据，通过 `DB_ROLL_PTR` 串成**链表**，从新到旧 |
| **Read View（读视图）** | 事务执行快照读时生成，记录当前活跃（未提交）的事务 ID 列表，用于判断哪些版本可见 |

**Read View 的判断规则：**

Read View 包含四个关键字段：
- `creator_trx_id`：当前事务自己的 ID
- `m_ids`：生成 Read View 时所有**活跃（未提交）**的事务 ID 列表
- `min_trx_id`：m_ids 中最小的值
- `max_trx_id`：系统分配给下一个事务的 ID（当前最大 ID + 1）

判断某一行版本（`DB_TRX_ID = trx_id`）是否可见：
1. `trx_id < min_trx_id` → ✅ 该版本在 Read View 之前提交，**可见**
2. `trx_id >= max_trx_id` → ❌ 该版本在 Read View 之后产生，**不可见**
3. `min_trx_id <= trx_id < max_trx_id` → 看 `trx_id` 是否在 `m_ids` 中：
   - 在 → ❌ 事务还未提交，**不可见**
   - 不在 → ✅ 事务已提交，**可见**

如果当前版本不可见，就沿 undo log 版本链往前找，直到找到一个可见的版本。

**RC 和 RR 的 Read View 区别：**

| 隔离级别 | Read View 生成时机 |
|---------|-------------------|
| RC（读已提交） | **每次** SELECT 都生成新的 Read View |
| RR（可重复读） | 事务中**第一次** SELECT 生成 Read View，后续复用 |

**背诵口诀：** MVCC = 隐藏列 + undo log 版本链 + Read View。RC 每次新建视图，RR 只建一次。

> 面试话术：「MVCC 通过三个组件实现：每行数据的隐藏字段记录事务 ID 和 undo log 指针，undo log 串成版本链保存历史版本，Read View 记录当前活跃事务列表用于判断可见性。RC 级别每次查询都创建新的 Read View 所以能看到其他事务的提交，RR 级别整个事务共用第一次的 Read View 所以看到的数据一致。」

### 9. MySQL 的锁有哪些？行锁、表锁、间隙锁？

**InnoDB 的锁按粒度分三级：表锁、行锁、间隙锁。行锁是 InnoDB 的核心优势。**

| 锁类型 | 粒度 | 说明 |
|--------|------|------|
| **表锁** | 整张表 | `LOCK TABLES`、DDL 操作、意向锁（IS/IX） |
| **行锁（Record Lock）** | 单行记录 | 锁住**索引记录**，只有通过索引查询才会用行锁 |
| **间隙锁（Gap Lock）** | 索引记录之间的间隙 | 锁住一个范围但**不包含记录本身**，防止其他事务在间隙中插入 |
| **临键锁（Next-Key Lock）** | 行锁 + 间隙锁 | **InnoDB 默认的锁**，锁住记录本身 + 前面的间隙，左开右闭区间 |

**行锁的两种模式：**

| 模式 | 说明 | SQL |
|------|------|-----|
| **共享锁（S 锁 / 读锁）** | 多个事务可以同时持有 | `SELECT ... LOCK IN SHARE MODE` |
| **排他锁（X 锁 / 写锁）** | 只有一个事务能持有 | `SELECT ... FOR UPDATE`、`INSERT`、`UPDATE`、`DELETE` |

**这题面试经常挖坑：行锁是锁行还是锁索引？**

**InnoDB 的行锁是锁索引记录，不是锁行。** 如果查询没有走索引，行锁会退化成**表锁**，锁住所有行。

```sql
-- 假设 name 没有索引
SELECT * FROM user WHERE name = '张三' FOR UPDATE;
-- 没走索引 → 全表扫描 → 锁所有行 → 等于表锁！
```

**间隙锁的作用：防止幻读**

在 RR 隔离级别下，`WHERE id > 5 AND id < 10 FOR UPDATE` 会锁住 (5, 10) 这个间隙，其他事务不能在这个范围内插入新记录。

**背诵口诀：** 行锁锁索引不锁行，没索引退化表锁。间隙锁防幻读，临键锁 = 行锁 + 间隙锁。

> 面试话术：「InnoDB 的锁按粒度分表锁、行锁和间隙锁。行锁实际锁的是索引记录，不走索引会退化成表锁。InnoDB 默认使用临键锁（行锁 + 间隙锁），在 RR 隔离级别下通过间隙锁防止幻读。」

### 10. 什么是死锁？MySQL 如何检测和处理死锁？

**死锁是两个或多个事务互相持有对方需要的锁，形成循环等待，谁也没法继续。**

```sql
-- 事务1：先锁 id=1，再锁 id=2
BEGIN; UPDATE t SET v=1 WHERE id=1; -- 拿到 id=1 的行锁
       UPDATE t SET v=1 WHERE id=2; -- 等事务2释放 id=2

-- 事务2：先锁 id=2，再锁 id=1
BEGIN; UPDATE t SET v=2 WHERE id=2; -- 拿到 id=2 的行锁
       UPDATE t SET v=2 WHERE id=1; -- 等事务1释放 id=1 → 死锁！
```

**InnoDB 的死锁检测和处理：**

| 机制 | 说明 |
|------|------|
| **等待超时** | `innodb_lock_wait_timeout`（默认 50 秒），超时自动回滚 |
| **死锁检测** | `innodb_deadlock_detect = ON`（默认开启），发现死锁后**立即回滚代价最小的事务**（undo log 最少的那个） |

**如何避免死锁？**
1. **固定加锁顺序**：所有事务按**相同的顺序**访问表和行
2. **尽量用索引访问数据**：避免行锁退化为表锁
3. **控制事务大小**：事务越小，持锁时间越短，死锁概率越低
4. **合理使用索引**：减少锁的范围

**背诵口诀：** InnoDB 自动检测死锁，回滚代价小的。预防靠固定顺序 + 短事务。

> 面试话术：「MySQL 死锁是多个事务循环等待对方持有的锁。InnoDB 默认开启死锁检测，发现后立即回滚 undo log 最少的事务。避免死锁的方法是固定加锁顺序、缩小事务范围、确保查询走索引。」

## 四、优化与架构
### 11. MySQL 的主从复制原理？

**MySQL 主从复制基于 binlog 实现，核心流程有三个线程：**

```
Master（主库）                    Slave（从库）
    │                                │
    │ ① Binlog Dump 线程             │
    │ ──── 发送 binlog ────→  ② IO 线程（接收并写入 relay log）
    │                                │
    │                         ③ SQL 线程（读 relay log 并重放）
```

| 步骤 | 线程 | 做什么 |
|------|------|--------|
| ① | Master 的 **Binlog Dump 线程** | 把 binlog 事件发送给 Slave |
| ② | Slave 的 **IO 线程** | 接收 Master 的 binlog，写入本地的 **relay log（中继日志）** |
| ③ | Slave 的 **SQL 线程** | 读取 relay log，解析并**重新执行** SQL，使数据与 Master 一致 |

**三种复制模式：**

| 模式 | 说明 | 数据安全 | 性能 |
|------|------|---------|------|
| **异步复制**（默认） | Master 写完 binlog 就返回，不等 Slave | ⚠️ Master 宕机可能丢数据 | **最快** |
| **半同步复制** | Master 等**至少一个** Slave 写入 relay log 才返回 | ✅ 较安全 | 稍慢 |
| **全同步复制** | Master 等**所有** Slave 都执行完才返回 | ✅ 最安全 | **最慢** |

**binlog 的三种格式：**

| 格式 | 记录内容 | 优缺点 |
|------|---------|--------|
| `STATEMENT` | 记录 SQL 语句 | 日志量小，但某些函数（如 `NOW()`、`UUID()`）可能导致主从不一致 |
| `ROW`（**推荐**） | 记录每行数据的变化 | 日志量大，但**主从一致性最好** |
| `MIXED` | 混合模式，一般用 STATEMENT，特殊情况自动切 ROW | 折中 |

**背诵口诀：** 三个线程：Dump 发、IO 收、SQL 放。异步快但可能丢，半同步等一个从库写完再返回。

> 面试话术：「MySQL 主从复制通过 binlog 实现，Master 的 Dump 线程发送 binlog，Slave 的 IO 线程接收写入 relay log，SQL 线程重放 relay log。默认异步复制性能好但可能丢数据，半同步复制等至少一个从库确认更安全。binlog 推荐 ROW 格式保证一致性。」

### 12. 如何优化慢查询？

**慢查询优化的核心思路：定位 → 分析 → 优化。**

**第一步：定位慢 SQL**
- 开启慢查询日志：`slow_query_log = ON`，`long_query_time = 1`（超过 1 秒记录）
- 用 `mysqldumpslow` 工具分析慢查询日志，找出最慢的 SQL

**第二步：用 EXPLAIN 分析执行计划**

| EXPLAIN 关键字段 | 含义 | 关注点 |
|-----------------|------|--------|
| `type` | 访问类型 | 从好到差：`system > const > eq_ref > ref > range > index > ALL`。出现 `ALL` 说明全表扫描 |
| `key` | 实际使用的索引 | `NULL` 说明没走索引 |
| `rows` | 预估扫描行数 | 越小越好 |
| `Extra` | 额外信息 | `Using filesort`（文件排序）和 `Using temporary`（临时表）要重点优化 |

**第三步：常见优化手段**

| 优化方向 | 具体做法 |
|---------|---------|
| **加索引** | 在 WHERE、ORDER BY、JOIN 的列上建索引 |
| **避免索引失效** | 不在索引列上用函数，注意类型转换，LIKE 不要 % 开头 |
| **覆盖索引** | 只查需要的列，避免 `SELECT *` |
| **优化 SQL** | 用小表驱动大表（`EXISTS` 替代 `IN`），分页用 `WHERE id > offset` 替代 `LIMIT offset, n` |
| **分页优化** | 大偏移量时先子查询定位 ID，再关联查数据 |
| **表结构优化** | 字段类型尽量小，避免 TEXT/BLOB，适度反范式 |

**深分页优化示例：**

```sql
-- ❌ 慢：LIMIT 100000, 10 要扫描前 10 万行再丢弃
SELECT * FROM orders ORDER BY id LIMIT 100000, 10;

-- ✅ 快：先定位 ID，再取数据
SELECT * FROM orders WHERE id > 100000 ORDER BY id LIMIT 10;
-- 或者子查询方式
SELECT * FROM orders INNER JOIN (SELECT id FROM orders ORDER BY id LIMIT 100000, 10) AS t ON orders.id = t.id;
```

**背诵口诀：** 慢查询三步走：开日志找 SQL → EXPLAIN 看执行计划 → 加索引改 SQL。

> 面试话术：「优化慢查询首先开启慢查询日志定位问题 SQL，然后用 EXPLAIN 分析执行计划，重点看 type 是否全表扫描、key 是否走了索引。优化手段包括加合适的索引、避免索引失效、覆盖索引减少回表、优化分页查询等。」

### 13. explain 的各个字段含义？

**EXPLAIN 是分析 SQL 执行计划的核心工具，关键字段如下：**

| 字段 | 含义 | 重点关注 |
|------|------|---------|
| `id` | 查询序号 | 数字越大越先执行，相同则从上到下 |
| `select_type` | 查询类型 | `SIMPLE`（简单）、`PRIMARY`（外层）、`SUBQUERY`（子查询） |
| `table` | 访问的表 | — |
| **`type`** | **访问类型（最重要）** | 从好到差：`system > const > eq_ref > ref > range > index > ALL` |
| `possible_keys` | 可能用到的索引 | — |
| **`key`** | **实际使用的索引** | `NULL` 表示没走索引 |
| `key_len` | 索引使用的字节数 | 越短越好，可以判断联合索引用了几列 |
| **`rows`** | **预估扫描行数** | 越小越好 |
| `filtered` | 经过条件过滤后的行比例 | 100% 最好，越小说明过滤效果越好 |
| **`Extra`** | **额外信息** | 见下表 |

**type 字段的详细含义：**

| type | 含义 | 性能 |
|------|------|------|
| `const` | 主键或唯一索引等值查询，最多一行 | ⭐⭐⭐⭐⭐ |
| `eq_ref` | JOIN 时使用主键或唯一索引，每个值最多一行 | ⭐⭐⭐⭐ |
| `ref` | 普通索引等值查询，可能多行 | ⭐⭐⭐ |
| `range` | 索引范围扫描（`BETWEEN`、`>`、`<`、`IN`） | ⭐⭐ |
| `index` | 全索引扫描（遍历整棵索引树） | ⭐ |
| `ALL` | **全表扫描** | ❌ 最差，需要优化 |

**Extra 字段常见值：**

| Extra | 含义 | 好坏 |
|-------|------|------|
| `Using index` | 覆盖索引，不回表 | ✅ 好 |
| `Using index condition` | 索引下推 | ✅ 好 |
| `Using where` | Server 层过滤 | 中性 |
| `Using filesort` | 额外排序（没走索引排序） | ⚠️ 需优化 |
| `Using temporary` | 使用临时表 | ⚠️ 需优化 |

**背诵口诀：** 看 type 看 key 看 rows 看 Extra。type 别 ALL，key 别 NULL，Extra 别 filesort。

> 面试话术：「EXPLAIN 最关键的四个字段是 type、key、rows 和 Extra。type 表示访问类型，ALL 是全表扫描需要优化；key 是实际使用的索引；rows 是预估扫描行数越小越好；Extra 中出现 Using filesort 或 Using temporary 说明需要优化排序或分组。」

### 14. 分库分表的策略？

**数据量太大（单表超过 500 万行或 2GB）时，可以通过分库分表来提升性能。**

| 方式 | 说明 | 解决的问题 |
|------|------|-----------|
| **垂直分表** | 把一张表的列拆到多张表中（如把大字段拆出去） | 减少单行数据量，提高查询效率 |
| **垂直分库** | 按**业务模块**拆数据库（用户库、订单库、商品库） | 解决单库连接数和 IO 瓶颈 |
| **水平分表** | 按某个字段（如 ID）把数据**分散到多张表** | 解决单表数据量过大 |
| **水平分库** | 按某个字段把数据**分散到多个数据库** | 解决单库存储和并发瓶颈 |

**水平分表的路由策略：**

| 策略 | 做法 | 优缺点 |
|------|------|--------|
| **取模** | `id % n` 决定分到哪张表 | 简单均匀，但扩容时要**数据迁移** |
| **范围** | `id 1~100万` → 表1，`100万~200万` → 表2 | 扩容方便，但可能**热点不均** |
| **一致性哈希** | hash 环分配 | 扩容时只迁移部分数据 |

**分库分表带来的问题：**
- **跨库 JOIN**：拆开后不能直接 JOIN，需要在应用层组装
- **分布式事务**：跨库操作无法用本地事务
- **全局 ID**：自增 ID 会冲突，需要分布式 ID 方案（雪花算法等）
- **排序分页**：每个分片排序后在应用层归并

**常用中间件：** ShardingSphere、MyCat

**背诵口诀：** 垂直按业务拆，水平按数据拆。取模均匀但扩容难，范围扩容易但可能不均。

> 面试话术：「分库分表分垂直和水平两种。垂直按业务拆，水平按数据分散。水平分表常用取模或范围路由，取模分布均匀但扩容要迁移数据，范围扩容方便但可能数据不均。分库分表会引入跨库 JOIN、分布式事务、全局 ID 等问题。」

### 15. 如何保证主从一致性？

**主从延迟是主从复制的核心问题，导致从库数据不是最新的。保证一致性的方案如下：**

| 方案 | 做法 | 适用场景 |
|------|------|---------|
| **强制走主库** | 对一致性要求高的读操作直接查主库 | 简单粗暴，但增加主库压力 |
| **半同步复制** | Master 等至少一个 Slave 确认写入 relay log | 保证至少一个从库有最新数据 |
| **延迟监控 + 路由** | 监控从库延迟（`SHOW SLAVE STATUS` 的 `Seconds_Behind_Master`），延迟大时自动路由到主库 | 常用方案 |
| **等待 GTID** | 写完主库后，等从库同步到相同 GTID 位置再读 | 强一致但会增加读延迟 |
| **缓存方案** | 写完主库后更新缓存，读缓存而不是从库 | 适合热点数据 |

**主从延迟的原因：**
- 网络延迟
- 从库单线程重放（MySQL 5.6 前 SQL 线程单线程，5.7+ 支持**并行复制**）
- 从库机器配置低
- 主库大事务（如大批量 DELETE/UPDATE）

**背诵口诀：** 强一致走主库，最终一致用半同步，实时监控延迟动态路由。

> 面试话术：「主从一致性的核心问题是主从延迟。解决方案有：关键业务强制走主库、使用半同步复制保证至少一个从库同步、监控延迟动态路由、写后更新缓存。MySQL 5.7+ 支持并行复制可以显著降低延迟。」
