# JVM

---

## 一、内存结构

### 1. JVM 的内存结构是怎样的？

**一句话总结**：JVM 内存分为 **5 个区域**，其中**堆**和**方法区**是线程共享的，**虚拟机栈**、**本地方法栈**和**程序计数器**是线程私有的。

```
JVM 运行时数据区
├── 线程共享
│   ├── 堆（Heap）—— 存对象实例，GC 的主战场
│   └── 方法区（Method Area）/ 元空间（Metaspace，JDK 8+）—— 存类信息、常量、静态变量
└── 线程私有
    ├── 虚拟机栈（VM Stack）—— 存方法的局部变量、操作数栈（每个方法对应一个栈帧）
    ├── 本地方法栈（Native Method Stack）—— 为 Native 方法（如 C/C++ 写的方法）服务
    └── 程序计数器（PC Register）—— 记录当前线程执行到哪条字节码指令
```

| 区域 | 线程共享？ | 存什么 | 会 OOM 吗？ |
|------|-----------|--------|------------|
| **堆** | ✅ | 对象实例、数组 | ✅ `OutOfMemoryError: Java heap space` |
| **方法区/元空间** | ✅ | 类信息、常量池、静态变量 | ✅ `OutOfMemoryError: Metaspace` |
| **虚拟机栈** | ❌ | 局部变量、方法调用链 | ✅ `StackOverflowError` |
| **本地方法栈** | ❌ | Native 方法调用 | ✅ `StackOverflowError` |
| **程序计数器** | ❌ | 当前线程执行的字节码行号 | ❌ **唯一不会 OOM 的区域** |

**⚠️ 面试挖坑提醒**：「JDK 8 方法区有什么变化？」—— JDK 7 及之前方法区叫"永久代"（PermGen），使用 JVM 堆内存，容易 OOM。JDK 8 开始改名为**元空间（Metaspace）**，使用**本地内存**（操作系统的内存），默认大小不固定，不容易溢出。

> **面试话术**：JVM 内存分为 5 个区域。线程共享的有堆和方法区，堆存放对象实例，方法区存放类信息和常量。线程私有的有虚拟机栈、本地方法栈和程序计数器。JDK 8 之后方法区改为元空间，不再使用 JVM 堆内存而是用本地内存。

### 2. 堆和栈有什么区别？

**一句话总结**：**栈**存方法的局部变量和调用关系（自动分配回收，速度快），**堆**存对象实例（需要垃圾回收（GC），空间大）。

| 对比项 | 栈（虚拟机栈） | 堆 |
|--------|--------------|-----|
| 存储内容 | 局部变量、方法调用 | **对象实例**、数组 |
| 线程关系 | 线程**私有** | 线程**共享** |
| 内存管理 | 方法结束**自动释放** | 需要 **GC 回收** |
| 大小 | 较小（一般 1MB） | 很大（可配置到几个 GB） |
| 速度 | **快** | 较慢 |
| 异常 | `StackOverflowError` | `OutOfMemoryError` |

**背诵口诀**：「**栈管运行，堆管存储**」

### 3. 一个对象在 JVM 中的创建过程是怎样的？

**一句话总结**：`new` 一个对象要经过 **5 步**：类加载检查 → 分配内存 → 初始化零值 → 设置对象头 → 执行构造方法。

| 步骤 | 做了什么 |
|------|---------|
| 1. **类加载检查** | 检查类是否已加载，没有就先执行类加载过程 |
| 2. **分配内存** | 在堆中划一块空间。分配方式：指针碰撞（内存连续时）或空闲列表（内存不连续时） |
| 3. **初始化零值** | 给所有字段设默认值（int 为 0，boolean 为 false，引用为 null），这就是为什么成员变量不赋值也有默认值 |
| 4. **设置对象头** | 写入对象的元信息：哈希码、GC 分代年龄、锁信息、所属类的指针等 |
| 5. **执行 `<init>`** | 调用构造方法，按程序员写的逻辑给字段赋值 |

**⚠️ 面试挖坑提醒**：「分配内存时怎么保证线程安全？」—— 两种方式：① **CAS + 失败重试**（详见 Java 并发第 7 题）；② **TLAB**（Thread Local Allocation Buffer，线程本地分配缓冲区）——每个线程在堆中预先分配一小块私有内存，分配对象时先在 TLAB 中分配，不够了再用 CAS。

### 4. 怎么判断对象可以被垃圾回收？

**一句话总结**：主流 JVM 用**可达性分析算法** —— 从一组叫 "GC Roots" 的起点出发，沿着引用链向下搜索，**搜不到的对象就是垃圾**，可以被回收。

**GC Roots 有哪些**（可以作为起点的对象）：
- 虚拟机栈中引用的对象（方法中的局部变量）
- 方法区中静态变量引用的对象（`static` 变量）
- 方法区中常量引用的对象（`static final` 常量）
- 本地方法栈中引用的对象（Native 方法）
- 被 `synchronized` 持有的对象

```
GC Root (如局部变量)
  └→ 对象A
       └→ 对象B    ← A、B 可达，不回收
  
对象C → 对象D      ← C、D 与 GC Root 无连接，可回收
```

**⚠️ 面试挖坑提醒**：「还有另一种判断方法叫"引用计数法"，为什么 JVM 不用？」—— 引用计数法给每个对象维护一个引用计数，被引用则 +1，但**无法解决循环引用**的问题（A 引用 B，B 引用 A，计数都不为 0 但实际上都是垃圾）。Python 用引用计数 + 循环检测，Java 直接用可达性分析。

## 二、垃圾回收

### 5. 常见的垃圾回收算法有哪些？

**一句话总结**：主要有 **4 种**算法 —— 标记-清除、复制、标记-整理、分代收集。实际 JVM 都用**分代收集**，新生代用复制算法，老年代用标记-整理算法。

| 算法 | 原理 | 优点 | 缺点 |
|------|------|------|------|
| **标记-清除** | 先标记存活对象，再清除未标记的 | 实现简单 | 产生大量**内存碎片** |
| **复制** | 把内存分两半，把存活对象复制到另一半，然后清空原来那半 | 无碎片，速度快 | 浪费**一半内存** |
| **标记-整理** | 标记存活对象后，让它们都**向一端移动**，再清理边界外的内存 | 无碎片，不浪费空间 | 移动对象**效率较低** |
| **分代收集** | 按对象年龄分区，不同区域用不同算法 | **综合最优** | 实现复杂 |

**分代收集的核心思想**：

```
堆内存
├── 新生代（Young）—— 用复制算法（对象朝生夕死，存活率低，复制成本小）
│   ├── Eden（8 份）
│   ├── Survivor From（1 份）
│   └── Survivor To（1 份）
└── 老年代（Old）—— 用标记-整理算法（对象存活率高，不适合复制）
```

**背诵口诀**：「**新生代复制，老年代整理，分代收集兼两者之利**」

---

### 6. 常见的垃圾收集器有哪些？CMS 和 G1 的区别？

**一句话总结**：CMS 追求**最短停顿时间**（用标记-清除算法，有碎片），G1 是 **JDK 9+ 的默认收集器**（用标记-整理算法，可预测停顿时间，无碎片）。

| 对比项 | CMS | G1 |
|--------|-----|-----|
| 算法 | **标记-清除** | **标记-整理** |
| 内存碎片 | ❌ 有碎片 | ✅ 基本无碎片 |
| 停顿控制 | 尽量短，但不可预测 | ✅ 可设置**期望最大停顿时间** |
| 堆的划分 | 传统分代（新生代/老年代） | 把堆分成多个**大小相等的 Region**，每个 Region 可以是新生代也可以是老年代 |
| 适用场景 | 对延迟敏感的应用 | **大堆内存**（6GB+）且对延迟有要求 |
| JDK 版本 | JDK 9 标记弃用，JDK 14 移除 | **JDK 9+ 默认收集器** |

**CMS 的 4 个阶段**：初始标记（短暂停顿）→ 并发标记 → 重新标记（短暂停顿）→ 并发清除

> **面试话术**：CMS 和 G1 最大的区别有三点：第一，CMS 用标记-清除算法会产生碎片，G1 用标记-整理基本不会；第二，G1 把堆分成多个 Region，不再是传统的新生代老年代物理分隔，更灵活；第三，G1 可以设置期望的最大停顿时间，CMS 做不到。JDK 9 之后 G1 是默认收集器，CMS 已经被弃用了。

### 7. Minor GC、Major GC、Full GC 有什么区别？什么时候触发？

**一句话总结**：**Minor GC** 只回收新生代，非常频繁且速度快；**Major GC** 只回收老年代；**Full GC** 回收**整个堆 + 方法区/元空间**，停顿时间最长，要尽量避免。

**⚠️ 术语提醒**：以下 Minor / Major / Full GC 的划分以 **HotSpot 分代收集器**（Serial、ParNew、CMS 等）的常见口径为主。G1 收集器的叫法有所不同：G1 更常见的是 **Young GC**（回收所有 Young Region）和 **Mixed GC**（回收所有 Young Region + 部分 Old Region），只有在 Mixed GC 来不及时才会退化成 Full GC。面试时如果前面刚聊完 G1，注意切换到 G1 的术语。

| GC 类型 | 回收范围 | 触发条件 | 停顿时间 |
|---------|---------|---------|---------|
| **Minor GC** | 新生代（Eden + Survivor） | Eden 区满了 | **很短**（毫秒级，新生代小且对象大部分朝生夕死） |
| **Major GC** | 老年代 | 老年代空间不足 | 较长（老年代对象多且存活率高） |
| **Full GC** | **整个堆 + 方法区/元空间（JDK 8+）** | 见下方触发条件 | **最长**（全量扫描，生产环境要尽量避免） |

**Full GC 的常见触发条件**（面试重点，以 HotSpot 为例）：

1. **老年代空间不足**：大对象或晋升对象太多，老年代放不下
2. **方法区/元空间不足**：加载的类太多（如大量动态代理），Metaspace 满了
3. **调用 `System.gc()`**：代码手动触发（只是"建议"JVM 做 Full GC，不保证执行，但 HotSpot 默认会执行）
4. **空间分配担保失败**：Minor GC 前 JVM 会检查老年代剩余空间是否够用，如果不够就直接触发 Full GC
5. **CMS 收集器的并发模式失败**：CMS 并发回收期间老年代空间不够了，退化为 Serial Old 做 Full GC

**背诵口诀**：「**Minor 清小区（新生代），Major 清老区，Full 全家扫**」

> **面试话术**：Minor GC 只回收新生代，Eden 区满了就触发，因为新生代的对象大部分很快就不用了，所以 Minor GC 很快也很频繁。Major GC 只回收老年代。Full GC 是整个堆加方法区一起回收，停顿时间最长。Full GC 常见的触发原因有老年代空间不足、元空间不足、手动调 System.gc()、以及空间分配担保失败等。生产环境要尽量减少 Full GC 的频率。需要注意的是，G1 收集器里更常说的是 Young GC 和 Mixed GC，概念上和传统的 Minor / Major GC 不完全等价。

### 8. 对象什么时候会晋升（进入）老年代？

**一句话总结**：对象通常在新生代被创建，经过多次 Minor GC 仍然存活后会被"晋升"到老年代。主要有 **4 种情况**会导致对象进入老年代。

| # | 晋升条件 | 说明 |
|---|---------|------|
| 1 | **年龄达到阈值** | 对象每熬过一次 Minor GC，年龄 +1（存在对象头的 Mark Word 中，详见第 15 题）。默认年龄到 **15** 就晋升老年代（`-XX:MaxTenuringThreshold` 可调） |
| 2 | **大对象直接进老年代** | 在 **Serial / ParNew** 等分代收集器下，超过 `-XX:PretenureSizeThreshold` 的对象直接分配到老年代，避免在 Eden 和 Survivor 之间来回复制。**G1 下没有这个参数**，大对象会进入专门的 **Humongous Region**（超过 Region 大小一半的对象） |
| 3 | **Survivor 区放不下** | Minor GC 后存活对象太多，Survivor 区装不下，溢出的对象直接送入老年代 |
| 4 | **动态年龄判定** | 如果 Survivor 区中**同一年龄的所有对象大小总和 ＞ Survivor 空间的一半**，那么年龄 ≥ 该年龄的对象直接晋升，不用等到 15 |

**背诵口诀**：「**年龄到了、长得太大、住不下了、同龄太多——四种情况进老年代**」

> **面试话术**：对象进入老年代有四种情况。第一，年龄达到阈值，默认 15 岁，对象每经历一次 Minor GC 长一岁；第二，大对象直接进老年代，不在新生代来回复制；第三，Minor GC 后 Survivor 区放不下了，溢出的对象直接进老年代；第四，动态年龄判定，如果 Survivor 中某个年龄段的对象占了超过一半空间，这个年龄及以上的对象直接晋升。

**⚠️ 面试挖坑提醒**：「年龄为什么默认是 15 而不是其他值？」—— 因为对象头的 Mark Word 中只用了 **4 个 bit** 来记录 GC 分代年龄，4 个 bit 能表示的最大值就是 15（二进制 1111）。所以即使你把 `-XX:MaxTenuringThreshold` 设大于 15 也没用。

**关联知识点**：对象创建过程中的"设置对象头"步骤（第 3 题）会在 Mark Word 中初始化 GC 年龄为 0，每次 Minor GC 存活后 +1。

## 三、类加载

### 9. 类加载过程是怎样的？

**一句话总结**：一个类从加载到可以使用，需要经过 **5 个阶段**：加载 → 验证 → 准备 → 解析 → 初始化。

| 阶段 | 做了什么 | 通俗理解 |
|------|---------|---------|
| **加载** | 读取 `.class` 字节码文件，在内存中创建 Class 对象 | 把"设计图纸"读进来 |
| **验证** | 检查字节码是否合法、安全 | 检查图纸有没有问题 |
| **准备** | 给类的**静态变量**分配内存并设**默认值**（零值） | 搭好架子，但还没装修 |
| **解析** | 把符号引用（名字）替换为直接引用（内存地址） | 把"门牌号"换成真实地址 |
| **初始化** | 执行静态代码块 `static {}`，给静态变量赋程序员写的值 | 正式装修完毕 |

**背诵口诀**：「**加验准解初**」（加载、验证、准备、解析、初始化）

**⚠️ 面试挖坑提醒**：「准备阶段 `static int a = 10`，a 的值是多少？」—— **0**！准备阶段只设默认零值，`a = 10` 要到**初始化阶段**才执行。但如果是 `static final int a = 10`（常量），在准备阶段就直接赋值为 10。

### 10. 什么是双亲委派模型？为什么要用它？

**一句话总结**：类加载器收到加载请求时，**先让父加载器去加载**，父加载器加载不了才自己加载。目的是**保证核心类的安全**，防止被篡改。

**类加载器层级**：

```
Bootstrap ClassLoader（启动类加载器，加载 JDK 核心类如 java.lang.String）
    └→ Extension ClassLoader（扩展类加载器，加载扩展包）
         └→ Application ClassLoader（应用类加载器，加载我们写的代码）
              └→ 自定义 ClassLoader
```

**工作流程（向上委托，向下加载）**：
1. 应用类加载器收到请求 → "爸，你帮我加载一下？"
2. 扩展类加载器收到请求 → "爸，你帮我加载一下？"
3. 启动类加载器：能加载就自己加载，加载不了就告诉儿子"你自己来"
4. 一层层往回传，直到有人能加载

**为什么需要双亲委派**：
- **防止核心类被篡改**：即使你自己写一个 `java.lang.String` 类，也不会被加载，因为启动类加载器已经加载了 JDK 的 String
- **避免类重复加载**：同一个类只会被加载一次

**⚠️ 常见追问**：「什么情况下会打破双亲委派？」—— ① **SPI 机制**（如 JDBC、SLF4J）：接口在 JDK 中定义（启动类加载器加载），但实现类在第三方 jar 中（应用类加载器加载），需要通过线程上下文类加载器"反向委派"；② **Tomcat**：每个 Web 应用需要隔离不同版本的类，所以每个应用有自己的类加载器。

## 四、调优与排查

### 11. Java 中有哪几种引用类型？

**一句话总结**：Java 有 **4 种引用**，从强到弱：强引用、软引用、弱引用、虚引用。GC 只有在内存不够时才回收软引用对象，弱引用下次 GC 就回收，虚引用不影响对象生命周期，等同于没有引用。

| 引用类型 | 回收时机 | 用途 |
|---------|---------|------|
| **强引用** | 只要有引用就**永不回收** | 普通的 `Object obj = new Object()` |
| **软引用** `SoftReference` | **内存不足时**才回收 | 缓存（内存够就留着，不够就清掉） |
| **弱引用** `WeakReference` | **下次 GC 时**就回收 | `ThreadLocalMap` 的 key（详见 Java 并发第 10 题） |
| **虚引用** `PhantomReference` | **不影响对象生命周期**（等同于没有引用），且无法通过虚引用获取对象 | 跟踪对象被回收的时机（用于堆外内存管理） |

**背诵口诀**：「**强不回、软内存不足回、弱 GC 就回、虚等于没有引用**」

---

### 12. 常用的 JVM 调优参数有哪些？

**一句话总结**：最常用的参数就是控制**堆大小**和选择**垃圾收集器**。

| 参数 | 含义 | 示例 |
|------|------|------|
| `-Xms` | 堆初始大小 | `-Xms512m` |
| `-Xmx` | 堆最大大小 | `-Xmx2g` |
| `-Xss` | 每个线程的栈大小 | `-Xss256k` |
| `-Xmn` | 新生代大小 | `-Xmn256m` |
| `-XX:MetaspaceSize` | 元空间初始大小 | `-XX:MetaspaceSize=256m` |
| `-XX:+UseG1GC` | 使用 G1 收集器 | JDK 9+ 默认 |
| `-XX:MaxGCPauseMillis` | G1 最大停顿时间目标 | `-XX:MaxGCPauseMillis=200` |
| `-XX:+HeapDumpOnOutOfMemoryError` | OOM 时自动导出堆快照 | **排查 OOM 必备** |

**背诵口诀**：「**Xms 初始、Xmx 最大、Xss 栈大小**」—— 生产环境建议 `-Xms` 和 `-Xmx` 设相同值，避免运行时频繁调整堆大小。

### 13. 线上出现 OOM 怎么排查？

**一句话总结**：OOM（内存溢出）排查分 **3 步**：① 看错误信息定位哪个区域溢出 → ② 导出堆转储文件 → ③ 用工具分析哪些对象占了最多内存。

**按 OOM 类型排查**：

| 错误信息 | 溢出区域 | 常见原因 |
|---------|---------|---------|
| `Java heap space` | 堆 | 对象太多没释放、大对象、内存泄漏 |
| `Metaspace` | 元空间 | 加载的类太多（如大量动态代理） |
| `StackOverflowError` | 栈 | 递归调用没有终止条件 |
| `unable to create native thread` | 操作系统 | 创建了太多线程 |

**排查流程**：

1. **加启动参数**：`-XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=/tmp/dump.hprof`，让 OOM 时自动生成堆转储文件
2. **用工具分析**：用 **MAT**（Eclipse Memory Analyzer）或 **JVisualVM** 打开 `.hprof` 文件
3. **找到大对象**：看哪些对象数量异常多或占内存异常大
4. **定位代码**：通过对象类型反推到具体代码，查找是否有**集合没清理**、**连接没关闭**、**缓存没设上限**等问题

### 14. 什么是内存泄漏？和内存溢出有什么区别？

**一句话总结**：**内存泄漏**（Memory Leak）是对象不再使用但无法被 GC 回收（引用没断开），积累久了就会导致**内存溢出**（OOM）。

| 对比项 | 内存泄漏 | 内存溢出 |
|--------|---------|---------|
| 含义 | 不用的对象无法被回收 | 内存不够用 |
| 关系 | 是**原因** | 是**结果** |
| 严重程度 | 隐蔽，慢慢积累 | 直接崩溃 |

**常见内存泄漏场景**：
- **集合类**：只往 `List`/`Map` 里加数据不删除
- **连接未关闭**：数据库连接、IO 流、网络连接用完没 `close()`
- **ThreadLocal 未 remove**：线程池中线程复用，ThreadLocal 的 value 不会自动清理（详见 Java 并发第 10 题）
- **监听器/回调**：注册了监听器但没有注销
- **静态集合**：`static Map` 中的对象生命周期跟类一样长

### 15. Java 对象头包含什么？和锁有什么关系？

**一句话总结**：每个 Java 对象在内存中都有一个**对象头**，其中的 **Mark Word** 存储了哈希码、GC 分代年龄、**锁状态标志**等信息。synchronized 的**锁升级**就是通过修改 Mark Word 实现的。

| 对象头组成 | 内容 |
|-----------|------|
| **Mark Word** | 哈希码、GC 年龄、锁状态（无锁/偏向锁/轻量级锁/重量级锁） |
| **Klass Pointer**（类型指针） | 指向类的元数据，表示"这个对象是哪个类的实例" |
| **数组长度**（仅数组对象） | 记录数组的长度 |

**锁升级过程**（与 Java 并发第 6 题 synchronized 相关，以 JDK 6~14 的 HotSpot 为主；JDK 15 默认关闭偏向锁，JDK 18+ 已移除）：

```
无锁 → 偏向锁（只有一个线程访问）→ 轻量级锁（CAS 自旋）→ 重量级锁（操作系统互斥量）
```

- **偏向锁**：只有一个线程访问时，Mark Word 记录线程 ID，后续该线程进入不需要加锁
- **轻量级锁**：有竞争但不激烈时，用 CAS 自旋尝试获取
- **重量级锁**：竞争激烈时，升级为操作系统级别的互斥锁（性能最差）

### 16. 什么是直接内存？

**一句话总结**：直接内存（堆外内存）**不属于 JVM 运行时数据区**，而是通过 NIO 的 `ByteBuffer.allocateDirect()` 在操作系统内存中直接分配的，**不受 GC 管理**。

| 对比项 | 堆内存 | 直接内存 |
|--------|--------|----------|
| 分配方式 | `new Object()` | `ByteBuffer.allocateDirect()` |
| GC 管理 | ✅ 受 GC 管理 | ❌ 不受 GC 直接管理 |
| 读写性能 | 需要从用户态拷贝到内核态 | IO 时**少一次堆内外拷贝**（不经过 JVM 堆，数据直接在堆外内存与内核之间传递），性能更好。注意：这里是减少 JVM 层的拷贝，不等于 OS 层面的零拷贝（sendfile/mmap，详见操作系统第 10 题） |
| 适用场景 | 普通对象 | **NIO 网络读写**（如 Netty） |

**⚠️ 面试挖坑提醒**：直接内存虽然不受 GC 管理，但如果分配过多也会导致 OOM（`OutOfMemoryError: Direct buffer memory`）。Netty 大量使用直接内存来提高网络 IO 性能。
