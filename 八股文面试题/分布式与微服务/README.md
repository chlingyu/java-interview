# 分布式与微服务

---

## 一、分布式理论

### 1. 什么是 CAP 理论？

**一句话总结**：分布式系统**不可能同时满足** C（一致性）、A（可用性）、P（分区容错）三个特性，最多只能满足其中两个。由于网络分区（P）是不可避免的，所以实际上是在 **CP 和 AP 之间选择**。

| 字母 | 含义 | 说明 |
|------|------|------|
| **C**（Consistency） | 一致性 | 所有节点读到的数据都是最新的 |
| **A**（Availability） | 可用性 | 每个请求都能得到响应（不保证是最新的） |
| **P**（Partition Tolerance） | 分区容错 | 网络分区时系统仍能运行 |

| 选择 | 含义 | 代表 |
|------|------|------|
| **CP** | 保证一致性，牺牲可用性 | ZooKeeper、HBase |
| **AP** | 保证可用性，牺牲一致性 | Eureka、Cassandra、DynamoDB |

---

### 2. 什么是 BASE 理论？

**一句话总结**：BASE 是对 CAP 中 AP 方案的延伸——不追求强一致性，而是追求**最终一致性**。

| 缩写 | 含义 | 通俗理解 |
|------|------|---------|
| **BA**（Basically Available） | 基本可用 | 允许部分功能降级（如搜索变慢但不挂） |
| **S**（Soft State） | 软状态 | 允许中间状态，数据不需要实时一致 |
| **E**（Eventually Consistent） | 最终一致 | 过一段时间后数据最终会一致 |

---

### 3. 分布式事务有哪些解决方案？

**一句话总结**：跨服务的操作需要保证事务一致性，常用方案有 **2PC、TCC、消息最终一致性、Seata**。

| 方案 | 原理 | 优缺点 |
|------|------|--------|
| **2PC（两阶段提交）** | 协调者先问"能不能提交？"→ 再通知"提交/回滚" | 强一致但性能差，有协调者单点问题 |
| **TCC** | Try（预留）→ Confirm（确认）→ Cancel（撤销） | 性能好但**代码侵入大**（要写 3 个方法） |
| **消息最终一致性** | 通过 MQ 保证最终一致性 | 实现简单，但只能保证**最终一致** |
| **Seata（AT 模式）** | 自动生成反向 SQL 进行补偿 | ✅ 代码侵入小，阿里开源，**推荐** |

---

### 4. 分布式 ID 怎么生成？

**一句话总结**：分库分表后数据库自增 ID 会重复，需要全局唯一 ID 方案。最常用**雪花算法（Snowflake）**。

| 方案 | 原理 | 优缺点 |
|------|------|--------|
| UUID | 随机生成 128 位字符串 | 无序，不适合做主键 |
| 数据库自增 | 单独一张表负责自增 | 有性能瓶颈 |
| Redis INCR | 用 Redis 的原子自增 | 依赖 Redis |
| **雪花算法** | 64 位 = 时间戳 + 机器 ID + 序列号 | ✅ **推荐**（有序、高性能、不依赖 DB） |

## 二、微服务组件

### 5. 微服务有哪些核心组件？

**一句话总结**：微服务架构的核心组件有 **注册中心、网关、远程调用、配置中心、熔断降级**。

| 组件 | 作用 | Spring Cloud 实现 | Dubbo 生态 |
|------|------|------------------|-----------|
| **注册中心** | 服务注册与发现 | Eureka / **Nacos** | Nacos / ZooKeeper |
| **网关** | 统一入口，路由、鉴权、限流 | **Spring Cloud Gateway** | — |
| **远程调用** | 服务间调用 | **OpenFeign** | Dubbo |
| **配置中心** | 集中管理配置 | **Nacos** / Spring Cloud Config | Nacos |
| **熔断降级** | 防止级联故障 | **Sentinel** / Hystrix | Sentinel |
| **负载均衡** | 请求分发 | **LoadBalancer** / Ribbon | Dubbo 内置 |

---

### 6. 什么是服务熔断和服务降级？

**一句话总结**：**熔断**是调用方发现被调用方异常率过高时**自动断开**调用（类似电路保险丝），**降级**是服务压力大时**主动关闭非核心功能**返回兜底数据。

| 概念 | 触发方 | 做法 | 举例 |
|------|--------|------|------|
| **熔断** | **自动**触发 | 检测到故障率超阈值，后续请求直接返回失败，不再调用 | 支付服务挂了，订单服务不再调用支付，直接返回"稍后重试" |
| **降级** | **主动**或自动 | 关闭非核心功能，返回默认数据 | 大促时关闭推荐、评价等非核心功能，保主链路 |

**熔断三种状态**：
```
关闭（正常调用）→ 失败率超阈值 → 打开（直接失败）→ 超时后 → 半开（放少量请求试探）→ 成功则关闭
```

---

### 7. 注册中心 Nacos 和 ZooKeeper 有什么区别？

**一句话总结**：**Nacos** 同时支持 **AP 和 CP** 模式（可切换），功能更全（注册中心 + 配置中心）；**ZooKeeper** 是 **CP** 模式，强一致但可用性略差。

| 对比项 | Nacos | ZooKeeper |
|--------|-------|-----------|
| CAP | AP 或 CP（可切换） | **CP** |
| 功能 | **注册中心 + 配置中心** | 注册中心 + 分布式协调（也可做配置管理、分布式锁、Leader 选举等，但不像 Nacos 那样开箱即用） |
| 健康检查 | 客户端心跳 + 服务端主动检测 | 客户端心跳 |
| 生态 | 阿里系，Spring Cloud Alibaba | Dubbo 传统方案 |

---

### 8. RPC 和 HTTP 有什么区别？

**一句话总结**：**RPC**（Remote Procedure Call，远程过程调用）是一种调用方式，**HTTP** 是一种传输协议。RPC 可以基于 HTTP 也可以基于 TCP，通常 RPC 框架性能更好。

| 对比项 | RPC（如 Dubbo） | HTTP（如 OpenFeign） |
|--------|----------------|---------------------|
| 传输协议 | 自定义二进制协议 / HTTP | HTTP |
| 序列化 | 高效的二进制序列化（如 Protobuf） | JSON（可读但体积大） |
| 性能 | **更好** | 相对较差 |
| 使用复杂度 | 可选 IDL 或接口定义，取决于 RPC 框架和协议 | **更简单**，像调用本地方法 |
| 跨语言 | 需要各语言客户端 | ✅ 天然跨语言 |

## 三、Spring Cloud 组件详解

### 9. Spring Cloud Gateway 的原理是什么？

**一句话总结**：Gateway 是微服务的**统一入口**，所有请求先经过 Gateway，再路由到具体的服务。核心工作流程是：**路由（Route）+ 断言（Predicate）+ 过滤器（Filter）**。

```
客户端请求 → Gateway → Predicate 匹配路由 → Filter 链处理 → 转发到目标服务
```

| 核心概念 | 作用 | 举例 |
|---------|------|------|
| **Route（路由）** | 定义请求转发到哪个服务 | `/api/user/**` → user-service |
| **Predicate（断言）** | 匹配条件（满足才走这个路由） | 按 Path、Header、Method 等匹配 |
| **Filter（过滤器）** | 请求/响应的拦截处理 | 鉴权、限流、日志、添加请求头 |

**Gateway 常见用途**：统一鉴权、限流熔断、请求日志、跨域处理、灰度发布

---

### 10. OpenFeign 的原理是什么？

**一句话总结**：OpenFeign 让**远程调用像调用本地方法一样简单**。底层通过 **JDK 动态代理**（详见设计模式第 3 题），拦截接口方法调用，拼装 HTTP 请求发送到目标服务。

```java
// 定义 Feign 接口（像本地接口一样写）
@FeignClient(name = "user-service")
public interface UserClient {
    @GetMapping("/user/{id}")
    User getById(@PathVariable Long id);
}

// 使用时直接注入调用，像调本地方法
@Autowired
private UserClient userClient;
User user = userClient.getById(1L);  // 实际发了一个 HTTP 请求
```

**底层流程**：
1. `@FeignClient` 接口被 Spring 扫描，通过**动态代理**生成实现类
2. 调用时代理类拦截方法，根据注解（`@GetMapping`）拼装 HTTP 请求
3. 通过**负载均衡**（LoadBalancer）选择一个服务实例
4. 发送 HTTP 请求，接收响应并反序列化

---

### 11. Nacos 作为配置中心怎么实现动态刷新？

**一句话总结**：Nacos 配置中心可以**集中管理所有服务的配置**，修改配置后**不需要重启服务**就能生效。客户端通过**长轮询**（Long Polling）机制感知配置变更并刷新。

| 功能 | 说明 |
|------|------|
| **集中管理** | 所有服务的配置统一存放在 Nacos，不再写在 `application.yml` 里 |
| **动态刷新** | 修改 Nacos 配置后，服务**自动获取最新值**，无需重启 |
| **多环境管理** | 通过 Namespace + Group 区分 dev/test/prod 环境 |
| **灰度发布** | 可以只对部分实例推送新配置 |

**使用方式**：在需要动态刷新的类上加 `@RefreshScope` 注解，配置变更时 Spring 会重新创建该 Bean。

---

### 12. Sentinel 的限流和熔断是怎么实现的？

**一句话总结**：**Sentinel**（阿里开源）通过**流量控制**和**熔断降级**保护服务。限流控制 QPS（每秒请求数），熔断在错误率过高时自动断开调用。

**限流规则**：

| 规则 | 说明 | 举例 |
|------|------|------|
| **QPS 限流** | 每秒请求数超过阈值就拒绝 | 接口 QPS 超过 100 就返回"系统繁忙" |
| **线程数限流** | 并发线程数超过阈值就拒绝 | 处理线程超过 50 个就拒绝新请求 |
| **热点参数限流** | 对某个参数值单独限流 | 对商品 ID=100 的请求限流（秒杀场景） |

**熔断规则**：

| 策略 | 触发条件 |
|------|---------|
| **慢调用比例** | 慢请求占比超过阈值 |
| **异常比例** | 异常请求占比超过阈值 |
| **异常数** | 异常请求数超过阈值 |

---

### 13. 微服务中一个请求的完整调用链路是怎样的？

**一句话总结**：一个请求从客户端发出，经过**网关 → 负载均衡 → 服务A → 远程调用服务B → 返回结果**，中间涉及注册中心、配置中心等组件的配合。

```
客户端
  ↓
Gateway（网关：路由、鉴权、限流）
  ↓
LoadBalancer（负载均衡：从 Nacos 获取服务列表，选一个实例）
  ↓
Service A（处理业务，需要调用 Service B）
  ↓
OpenFeign（远程调用：拼装 HTTP 请求）
  ↓
LoadBalancer（再次负载均衡，选择 Service B 的实例）
  ↓
Service B（返回结果）
  ↓
原路返回 → 客户端
```

---

### 14. 负载均衡有哪些策略？

**一句话总结**：负载均衡分为**服务端负载均衡**（如 Nginx）和**客户端负载均衡**（如 Spring Cloud LoadBalancer）。微服务中常用客户端负载均衡。

| 策略 | 原理 | 适用场景 |
|------|------|---------|
| **轮询（Round Robin）** | 按顺序依次分配 | 服务器性能相当时（**默认策略**） |
| **随机（Random）** | 随机选择一台 | 简单场景 |
| **加权轮询** | 性能好的服务器分配更多请求 | 服务器性能不均 |
| **最少连接** | 选择当前连接数最少的 | 请求处理时间差异大 |
| **一致性哈希** | 相同参数的请求打到同一台 | 需要会话保持（缓存亲和） |

### 15. Spring Cloud 和 Dubbo 有什么区别？

**一句话总结**：**Spring Cloud** 是一整套微服务方案，常见服务调用方式是 **HTTP/REST**；**Dubbo** 是高性能 RPC 框架，经典 Dubbo 协议常见 **TCP 长连接**，Dubbo 3 的 Triple 也支持 **HTTP/2**。目前主流趋势是 **Spring Cloud Alibaba**（Spring Cloud + Nacos + Sentinel + Seata）。

| 对比项 | Spring Cloud | Dubbo |
|--------|-------------|-------|
| 定位 | **微服务全家桶** | **RPC 框架** |
| 通信方式 | 常见是 HTTP（RESTful） | 经典 Dubbo 协议常见 **TCP 长连接**；Dubbo 3 Triple 也支持 **HTTP/2** |
| 注册中心 | Eureka / Nacos | ZooKeeper / Nacos |
| 服务调用 | OpenFeign | Dubbo 协议 |
| 配置中心 | ✅ Nacos / Config | ❌ 需要额外集成 |
| 网关 | ✅ Gateway | ❌ 需要额外集成 |
| 生态完整度 | **更完整** | 需要自己搭配 |
| 性能 | 一般（HTTP + JSON） | 经典 Dubbo 协议通常更高；若走 Triple/HTTP/2，也要结合序列化和网络模型看 |

> **面试话术**：Spring Cloud 胜在生态完整、开箱即用，适合快速开发；Dubbo 胜在高性能、适合大规模内部服务通信。目前趋势是融合两者优势，用 Spring Cloud Alibaba 做框架，Dubbo 做内部高性能通信。

### 16. Sentinel 底层用了哪些限流算法？

**一句话总结**：Sentinel 主要用了**滑动时间窗口**做 QPS 统计和快速失败限流，配合**漏桶**做匀速排队。面试关键是把 4 种限流算法的区别讲清楚。

**四种限流算法对比**：

| 算法 | 原理（一句话） | 优点 | 缺点 |
|------|--------------|------|------|
| **固定窗口** | 把时间切成固定长度的格子（如每 1 秒一个），格子内计数超阈值就拒绝 | 实现最简单 | **临界突变**：两个窗口交界处可能放过 2 倍流量 |
| **滑动窗口** | 窗口不固定，而是像"移动的尺子"一样随时间滑动，每个小格子单独计数 | 解决了临界突变 | 实现比固定窗口复杂一点 |
| **漏桶** | 请求先进桶排队，桶以**固定速率**往外漏水（处理请求），桶满则拒绝 | 流量绝对匀速 | 无法应对突发流量（桶满就丢） |
| **令牌桶** | 以固定速率往桶里放令牌，请求来了取一个令牌，取到就通过，桶空就拒绝 | **允许一定突发**（桶里攒的令牌可以一次用掉） | 实现相对复杂 |

**Sentinel 怎么用的**：
- **默认 QPS 限流**：用**滑动时间窗口**。Sentinel 把 1 秒分成若干小格子（默认 2 个，即每 500 毫秒一格），统计窗口内的总请求数。这样就不会出现固定窗口的临界突变问题
- **匀速排队模式**：用**漏桶**（实际实现基于上一次通过时间计算，以固定间隔放行请求）。请求排队等待，超过最大等待时间才拒绝

> **背诵口诀**：「固定有临界，滑动解决它；漏桶太死板，令牌能突发。Sentinel 默认滑动窗口，排队用漏桶」

> **面试话术**：Sentinel 的核心限流算法是滑动时间窗口，它把 1 秒切成多个小时间片分别计数，解决了固定窗口在边界处可能放过两倍流量的问题。如果需要匀速排队（比如消息削峰），还可以用漏桶模式，按固定间隔放行请求，多余的排队等待。

**⚠️ 面试挖坑提醒**：
- 面试官可能问「漏桶和令牌桶的区别」——核心区别是**漏桶强制匀速**，令牌桶**允许一定程度的突发流量**（桶里攒了令牌就能一次用掉）
- 「Sentinel 用的是哪个算法？」——不要只说一个，要区分：**QPS 统计和快速失败用滑动窗口，匀速排队用漏桶**

### 17. Seata 的 AT 模式是怎么工作的？

**一句话总结**：Seata AT 模式是一种**自动补偿型**分布式事务方案。它的核心思路是：各个服务先各自提交本地事务、释放数据库本地锁，同时**自动记录回滚日志**（undo log），如果有服务失败，就用回滚日志把数据还原回去。注意：提交前必须先获取 **Seata 全局锁**，全局锁会持有到全局事务结束。代码侵入极小，加一个 `@GlobalTransactional` 注解就行。

**三大角色**：

| 角色 | 全称 | 作用 |
|------|------|------|
| **TC** | Transaction Coordinator（事务协调器） | 独立部署的 Seata Server，负责维护全局事务状态，协调各分支的提交或回滚 |
| **TM** | Transaction Manager（事务管理器） | 发起全局事务的那个服务（加 `@GlobalTransactional` 的方法所在服务），向 TC 申请开启、提交或回滚全局事务 |
| **RM** | Resource Manager（资源管理器） | 每个参与事务的服务中的数据源代理，负责管理分支事务的注册、状态汇报和本地回滚 |

**两阶段流程**：

```
第一阶段（业务执行 + 记录快照）：
  ① TM 向 TC 申请开启全局事务，获得全局事务 ID（XID）
  ② 各服务执行本地 SQL 前，RM 自动记录「修改前快照」（beforeImage）
  ③ 执行业务 SQL
  ④ RM 自动记录「修改后快照」（afterImage），前后快照一起存入 undo_log 表
  ⑤ 向 TC 申请全局锁 → 拿到后提交本地事务，释放数据库本地锁（但全局锁仍持有！）

第二阶段（提交或回滚）：
  ✅ 全部成功 → TC 通知各 RM 异步删除 undo_log（很快）
  ❌ 有失败 → TC 通知各 RM 用 undo_log 中的 beforeImage 生成反向 SQL，还原数据
```

**跟传统 2PC 的区别**：传统两阶段提交（详见本章第 3 题）在第一阶段不提交、一直持有**数据库本地锁**等协调者通知，**性能很差**。Seata AT 在第一阶段就提交了本地事务、释放了数据库本地锁（虽然仍持有 Seata 全局锁，但全局锁粒度小、不阻塞其他非全局事务的数据库操作），只在需要回滚时才用 undo_log 补偿，**性能好得多**。

> **背诵口诀**：「一阶段提交记快照，二阶段成功删日志、失败反向补偿」

> **面试话术**：Seata AT 模式的核心是"先提交再补偿"。第一阶段各服务执行完 SQL 就直接提交本地事务，同时自动记录修改前后的数据快照到 undo_log 表。如果所有分支都成功，TC 通知大家异步删掉 undo_log 就行；如果有分支失败，TC 通知用 undo_log 里的快照生成反向 SQL 回滚数据。整个过程对业务代码几乎没有侵入，只需要在入口方法加一个 `@GlobalTransactional` 注解。

**⚠️ 面试挖坑提醒**：
- 「AT 模式有什么缺点？」——因为第一阶段就提交了，存在**短暂的数据不一致**（其他事务可能读到中间状态），所以 AT 模式只保证**最终一致性**，不是强一致性
- 「undo_log 是谁生成的？」——是 Seata 的**数据源代理**自动生成的，不需要开发者手写
- 「如果回滚时发现数据被其他事务改了怎么办？」——Seata 会用 afterImage 做**脏数据校验**，如果发现当前数据和 afterImage 不一致，说明被别人改过了，会抛异常需要人工介入

### 18. TCC 模式和 AT 模式有什么区别？TCC 的空回滚、幂等、悬挂问题怎么解决？

**一句话总结**：TCC（Try-Confirm-Cancel）是**业务层面**的分布式事务方案，每个操作要手写 3 个方法（预留、确认、撤销），代码侵入大但不依赖数据库事务，适合**高性能、强隔离**的场景。

**TCC 三阶段**：

| 阶段 | 做什么 | 举例（转账 100 元） |
|------|--------|-------------------|
| **Try（预留）** | 做业务检查 + **冻结资源**，但不真正扣款 | 检查余额够不够，冻结 100 元（余额不减，冻结金额 +100） |
| **Confirm（确认）** | Try 成功后，**真正执行**业务，不再做检查 | 余额 -100，冻结金额 -100，对方余额 +100 |
| **Cancel（撤销）** | Try 失败后，**释放冻结**的资源 | 冻结金额 -100，余额恢复 |

**TCC vs AT 对比**：

| 对比项 | AT 模式（详见第 17 题） | TCC 模式 |
|--------|----------------------|---------|
| 侵入性 | **极小**（加注解就行） | **大**（要手写 3 个方法） |
| 一致性 | 最终一致性 | 可做到**准强一致性**（资源在 Try 阶段就冻结了） |
| 性能 | 有全局锁，并发一般 | **更好**（不用全局锁，资源在业务层冻结） |
| 适用场景 | 普通业务（订单、库存） | **资金类**、对一致性和性能要求高的场景 |
| 回滚方式 | undo_log 自动补偿 | **Cancel 方法**手动补偿 |

**⚠️ TCC 三大经典坑**：

**① 空回滚**：Try 方法还没执行（比如网络超时），Cancel 却先被调用了
- **问题**：Cancel 要撤销什么？Try 都没执行，没有可撤销的资源
- **解决**：在 Try 前插入一条**事务控制记录**（记全局事务 ID + 分支 ID）。Cancel 执行时先查这条记录，如果 Try 没执行过，就跳过撤销逻辑，直接返回成功

**② 幂等**：Confirm 或 Cancel 可能被**重复调用**（比如网络重试）
- **问题**：重复扣款、重复释放资源
- **解决**：在事务控制表里记录**当前阶段状态**（已 Try / 已 Confirm / 已 Cancel），每次执行前先检查，已执行过就直接返回成功

**③ 悬挂**：Cancel 比 Try **先执行**了（网络延迟导致 Try 请求晚到）
- **问题**：Cancel 已经执行了，Try 又来冻结资源，但没有人再来释放
- **解决**：Try 执行前先查事务控制表，如果发现 Cancel 已执行，就**拒绝执行 Try**

> **背诵口诀**：「空回滚查有没有 Try，幂等查有没有做过，悬挂查有没有 Cancel 先跑。三个问题一张控制表全解决」

> **面试话术**：TCC 的核心思路是在业务层面实现"预留-确认-撤销"三个阶段，不依赖数据库的 undo_log。它的优点是性能好、隔离性强，但缺点是代码侵入大，而且要处理空回滚、幂等和悬挂三个经典问题。这三个问题的解决思路都是一样的——加一张事务控制表记录每个阶段的执行状态，执行前先检查。

### 19. 接口幂等性怎么设计？

**一句话总结**：**幂等性**就是「同一个操作执行一次和执行多次，结果都一样」。接口幂等性设计的目的是**防止重复请求导致数据出错**（比如用户重复点击下单、网络重试导致重复扣款）。

**为什么需要幂等**：
- 用户手抖，连续点了 2 次"提交订单"
- 网络超时，客户端自动重试
- MQ 消费者重复消费消息（详见消息队列第 5 题）
- 调用方/网关/客户端配置了重试机制（如 Feign 原生默认重试部分 IO 异常，Spring Cloud OpenFeign 则默认关闭重试）

**常见幂等方案**：

| 方案 | 原理 | 适用场景 | 注意点 |
|------|------|---------|--------|
| **Token 令牌机制** | 请求前先获取唯一 Token，提交时带上 Token，服务端原子校验并删除（Redis DEL），重复请求因 Token 已删而被拒绝 | **表单提交**（防重复下单） | Token 要原子校验+删除，不能先查再删（有并发问题） |
| **唯一业务 ID** | 用订单号、流水号等唯一标识做去重，插入前先查是否已处理过 | **支付**、转账 | 需要唯一索引兜底，防止并发插入 |
| **数据库唯一索引** | 利用数据库唯一约束，重复插入直接报错 | 简单场景 | 只能防重复插入，不能防重复更新 |
| **乐观锁（版本号）** | 更新时带版本号 `WHERE version = xx`，重复请求因版本号已变而更新 0 行 | **更新操作** | 需要数据库表加 version 字段 |
| **状态机** | 业务有固定的状态流转（如 待支付→已支付→已发货），不满足当前状态的请求直接拒绝 | **订单状态变更** | 状态只能单向流转 |

**最推荐的方案——Token 令牌机制流程**：

```
① 客户端进入下单页面时，先请求服务端获取一个唯一 Token
② 服务端生成 Token，存入 Redis（设过期时间），返回给客户端
③ 客户端提交订单时，把 Token 放在请求头里一起传过来
④ 服务端用 Redis 的 DEL 命令删除 Token（原子操作）：
   - 删除成功（返回 1）→ 说明是第一次请求，正常处理
   - 删除失败（返回 0）→ 说明 Token 已被用过，是重复请求，直接拒绝
```

> **背诵口诀**：「查重靠唯一标识，写入靠唯一索引，更新靠版本号，提交靠 Token」

> **面试话术**：接口幂等性设计的核心思路是给每次请求打上唯一标记，服务端通过这个标记判断是不是重复请求。最常用的方案是 Token 机制——进页面先拿 Token 存 Redis，提交时原子删除校验。对于更新操作，用乐观锁的版本号机制就行。再往上还可以结合状态机，限制业务状态只能单向流转。

**⚠️ 面试挖坑提醒**：
- 「HTTP 语义上 GET、HEAD、PUT、DELETE 都是幂等的，POST 通常不是」——面试官可能先问你 HTTP 方法的幂等性，再引到业务幂等设计。但要注意：**HTTP 语义幂等 ≠ 业务幂等**，接口实际是否幂等还要看具体实现
- 「Token 校验为什么用 DEL 不用 GET+DEL？」——因为 GET 再 DEL 不是原子操作，两个请求可能同时 GET 到 Token 都通过校验。用 DEL 命令本身返回值判断（成功返回 1），是**原子操作**
